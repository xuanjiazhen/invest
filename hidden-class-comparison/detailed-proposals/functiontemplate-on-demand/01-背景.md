# FunctionTemplate compact recipe：背景

## 1. 问题定义

ArkVM 在首次解析 class literal 时，为每个类方法分配一个 `FunctionTemplate`。该对象保存 `Method`、`Module`、`RawProfileTypeInfoCell` 和 `Length`，当前 frozen revision 下 shallow size 为 40 B。ClassLiteral 缓存在 ConstantPool 中，并通过 literal array 长期持有这些对象。

FunctionTemplate 并不是“方法从未调用前的待创建函数”。class definition 每次执行时，`ClassInfoExtractor` 会立即遍历 literal array，将模板实例化为新的 JSFunction；FunctionTemplate 随后继续常驻，用于下一次执行同一 class definition 时再次创建 JSFunction，并保留跨次实例化共享的 ProfileTypeInfoCell。因此，本需求不采用“首次 NewJSFunction 时才创建模板”或“首次实例化后删除模板”的旧假设。

本需求处理的冗余是：四个字段各占一个独立 40 B TaggedObject，而它们已由 ClassLiteral 槽位天然分组，可以改为 ClassLiteral 持有的紧凑 recipe array，同时保持重复类定义、反馈 cell、AOT、hot patch 和 Sendable 语义。

## 2. 现状对象与生命周期

### 2.1 创建

class literal 解码遇到 `METHODAFFILIATE` 时，`LiteralDataExtractor::DefineFunctionTemplate` 创建 Method、生成 Module，并按类类型调用 `NewFunctionTemplate` 或 `NewSFunctionTemplate`。普通模板分配在 LocalHeap，Sendable 模板分配在 SharedHeap。

### 2.2 消费

普通类和 Sendable 类的 property/element/accessor 路径均以 `IsFunctionTemplate()` 识别模板。普通类通过 `CreateJSFunctionFromTemplate` 创建 JSFunction，再由 `UpdateProfileTypeInfoCell` 将模板中的 Empty cell 升级为独立 cell；后续重复类定义复用并升级同一 cell。Sendable 类通过 `CreateSFunctionFromTemplate` 创建 shared function。

### 2.3 长期持有

ClassLiteral 在 literal array 已完整生成后创建并放入 ConstantPool cache。普通类直接写 cache；Sendable 类使用 CAS 发布。只要 ClassLiteral 仍在 cache 中，其 FunctionTemplate 就继续存活。

### 2.4 旁路消费者

- AOT snapshot 从 FunctionTemplate.Method 读取 method offset。
- hot patch 遍历 heap 中的 FunctionTemplate，按 Method 定位后修改 Module，并在热补丁路径重置 RawProfileTypeInfoCell。
- GC visitor 扫描 FunctionTemplate 的三个 tagged 字段。
- `panda_file_translator.cpp` 有两个预解析 class literal 的直接创建入口。

## 3. 真实存量

15 份输入均满足：

- FunctionTemplate shallow size 全部为 40 B；
- 每个 FunctionTemplate 恰好由一个 ClassLiteral 的 literal array 持有；
- 无 unowned 或 multiply-owned FunctionTemplate；
- legacy schema 使用 `function_template/class_literal`，新版 schema 使用 `ArkInternalFunctionTemplate/ClassLiteral`，复算脚本按精确 alias 处理。

| 样本 | FunctionTemplate 存量 | shallow | `N>=2` 模型覆盖 | 当前覆盖 shallow | recipe 成本 | 条件净 shallow |
|---|---:|---:|---:|---:|---:|---:|
| Top13 汇总 | 954,059 | 36.394 MiB | 913,819 | 34.859 MiB | 23.654 MiB | 11.206 MiB |
| 快手前台 | 57,864 | 2.207 MiB | 54,918 | 2.095 MiB | 1.421 MiB | 0.674 MiB |
| 快手后台 | 55,523 | 2.118 MiB | 52,700 | 2.010 MiB | 1.364 MiB | 0.647 MiB |

Top13 是 13 个独立应用进程快照的算术汇总，不代表单进程收益。快手前台与后台是两个独立终态，不能相加或相减。

## 4. 收益口径

对每个命中 compact 表示的 ClassLiteral：

- `N`：该 ClassLiteral 拥有的 FunctionTemplate 数，且 `N >= 2`；
- `C`：命中的 ClassLiteral 数；
- 原对象成本：`40N`；
- recipe array：16 B 头 + 每模板 3 个 tagged slot，即 `16 + 24N`；
- compact ClassLiteral 相比旧 ClassLiteral 多一个 tagged 字段，即 8 B；
- 总元数据成本：`24N + 24C`；
- 条件净 shallow：`40N - 24N - 24C = 16N - 24C`。

每个命中类均满足 `N>=2`，单类净收益至少 8 B，不依赖跨类或跨应用均摊。未命中类继续使用旧 FunctionTemplate，不增加字段或索引成本。

上述数值是终态 shallow bytes 模型，不是 committed、RSS 或 PSS。物理内存收益只接受同版本、同镜像、同账号数据、同温度、同场景 clean A/B。

## 5. 独立核算边界

本需求只核算 FunctionTemplate 替换为 compact recipe 的收益，不计入：

- LayoutInfo sharing；
- Local ConstantPool；
- Native Interop；
- LayoutInfo Attribute packing；
- ProfileTypeInfoCell 对象自身的延迟分配或裁剪；
- ABC 编译期 DCE；
- JSFunction、Method、Module 或 ClassLiteral cache 的其他优化。
