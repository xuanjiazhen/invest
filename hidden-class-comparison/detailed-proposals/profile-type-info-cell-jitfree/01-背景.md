# ProfileTypeInfoCell 编译期裁槽 —— 背景

本文件介绍 `MachineCode` 和 `Handle` 两个字段的编译期裁槽依据。

## 1. ProfileTypeInfoCell 的作用

`ProfileTypeInfoCell` 是 `JSFunction` 与反馈数组之间的一级间接对象。函数通过 `JSFunction::RawProfileTypeInfo` 指向 cell，cell 的 `Value` 再指向 `ProfileTypeInfo`；解释器、IC、AOT、PGO 和 JIT 由此取得属性访问、调用和操作类型等反馈（`js_function.h:412-436`、`ic/profile_type_info_cell.h:34-40`）。

cell 还承载两项能力专用状态：

- `MachineCode`：JIT 机器码弱缓存；
- `Handle`：PGO define-class 使用的弱构造函数引用。

同一函数定义位置创建的多个闭包可以指向同一个 cell。父函数的 `ProfileTypeInfo[slotId]` 保存这份共享记录，闭包通过各自的 `RawProfileTypeInfo` 引用它；运行时以 `CELL_0/1/N` 表示这份记录被闭包复用的级别（`interpreter/interpreter-inl.cpp:1046-1061`、`ic/profile_type_info_cell.h:47-59`）。本方案不改变创建、共享或转级行为，只缩小所有 cell 的固定布局。

## 2. 当前布局（32 B）

```text
JSFunction（仅列相关字段）
+-----------------------------------+
| RawProfileTypeInfo ---------------+----+
+-----------------------------------+    |
| MachineCode（JSFunction 自有）    |    |  不在本方案范围
+-----------------------------------+    |
                                         v
                         ProfileTypeInfoCell（当前 32 B）
                         +-----------------------------+
                         | TaggedObject header     8 B |
                         +-----------------------------+
                         | Value ----------------------+----> ProfileTypeInfo
                         +-----------------------------+
                         | MachineCode (weak)      8 B |      JIT 专用缓存
                         +-----------------------------+
                         | Handle (weak)           8 B |      PGO define-class
                         +-----------------------------+
```

源码：`ecmascript/ic/profile_type_info_cell.h`。

| 偏移 | 大小 | 字段 | 语义 | 裁剪条件 |
|---:|---:|---|---|---|
| 0 | 8 B | `TaggedObject` header | 对象头 | 保留 |
| 8 | 8 B | `Value` | `ProfileTypeInfo` 或空值 | 始终保留 |
| 16 | 8 B | `MachineCode` | JIT `MachineCode` 弱引用缓存或 `Hole` | 编译期 JIT-free 删除 |
| 24 | 8 B | `Handle` | PGO define-class 的弱构造函数引用 | 编译期 PGO-free 删除 |
| **合计** | **32 B** | `ProfileTypeInfoCell::SIZE` | | |

创建时初始化为 `Value=创建参数`、`MachineCode=Hole`、`Handle=Undefined`；目标档位只初始化实际存在的字段。

## 3. 字段消费者

### 3.1 Value：公共反馈字段

```text
JSFunction::RawProfileTypeInfo
  → ProfileTypeInfoCell::Value
  → ProfileTypeInfo
```

属性访问 IC、操作类型反馈、类定义反馈、PGO、AOT 和 JIT 均可能使用 `Value`。关闭 JIT 或 PGO 都不能删除整个 cell，也不能删除 `Value`。

### 3.2 MachineCode：JIT 专用槽

```text
JitTask::InstallCode
  → JSFunction::SetJitMachineCodeCache
  → ProfileTypeInfoCell::SetMachineCode(weak MachineCode)
```

已确认的语义消费者：

- JIT 安装写入弱缓存（`jit/jit_task.cpp:388`）；
- deopt 清理回写 `Hole`（`deoptimizer/deoptimizer.cpp:684`）；
- JIT 运行时诊断读取状态（`stubs/runtime_stubs.cpp:4878`）。

上述消费者均属于 JIT 能力闭包。编译期确定无 Fast JIT、Baseline JIT、OSR、JIT deopt 和相关诊断时，该槽无业务消费者，可从 32 B 布局删除。

### 3.3 Handle：PGO 专用槽

```text
ProfilerStubBuilder::ProfileDefineClass
  → 向 Handle 写入 weakCtor
PGOProfiler::DumpDefineClass
  → 读取 Handle 并生成 PGO define 记录
```

直接读写位置：

- profiler stub 固定偏移读写（`compiler/profiler_stub_builder.cpp:155-160`）；
- `PGOProfiler` 读取并生成 `PGODefineOpType`（`pgo_profiler/pgo_profiler.cpp:1338-1393`）；
- local/shared factory 初始化（`object_factory.cpp:5560`、`shared_object_factory.cpp:597`）。

AOT 编译器可以在后续读取 PGO 生成的 `.ap` 数据，但没有直接读取 cell 的 `Handle`。PGO 本身可在没有 AOT 时独立初始化、采集和保存 `.ap`；因此 `Handle` 的删除条件是**编译期 PGO-free**，不是 AOT-free。

### 3.4 JSFunction 自有 MachineCode 不在范围内

`JSFunction::MachineCode` 是函数对象上的独立字段，具有 JIT 入口、deopt、栈回溯和调试等消费者。本方案只处理 `ProfileTypeInfoCell::MachineCode`，不修改已冻结的 `JSFunction` 布局。

## 4. 编译期能力与目标布局

方案层能力闭包如下，落地时由冻结 revision 的既有 GN feature 汇总生成：

```text
ARK_PROFILE_CELL_HAS_MACHINE_CODE = FAST_JIT_ENABLED || BASELINE_JIT_ENABLED
                                    || OSR_ENABLED || JIT_DEOPT_ENABLED
                                    || JIT_CODE_DIAGNOSTICS_ENABLED
ARK_PROFILE_CELL_HAS_HANDLE       = PGO_PROFILER_ENABLED
```

| 构建能力 | cell 布局 | 尺寸 | 本方案阶段 |
|---|---|---:|---|
| JIT + PGO | header + Value + MachineCode + Handle | 32 B | 基线/兼容档 |
| JIT-free + PGO | header + Value + Handle | 24 B | 阶段一 |
| JIT-free + PGO-free | header + Value | 16 B | 阶段二 |

运行时 `--jit=false`、不存在 AOT 文件或本次运行未触发 PGO，均不能切换对象布局。同一镜像只能使用一种由编译期能力决定的尺寸。
