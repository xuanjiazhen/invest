## 1. 结论

选择 D1：**保留当前 registration-time `JSFunction + JSNativePointer` 对象图，只把每函数一次独立 `new NapiFunctionInfo` 改为每次 `napi_define_class` 一次连续 native table allocation；真实调用时才从 compact entry 解析 callback、data、env 与 scopeId。**

D1 的 lazy 效果只发生在 native binding metadata 层：

1. 不再为目标函数创建完整、独立的 `NapiFunctionInfo` native allocation；
2. 注册期仍必须复制调用方只在当前调用有效的 `{callback, data}`，不能把这 16 B 推迟到首次读取或首次调用；
3. `env` 与注册时 `scopeId` 在一次 `napi_define_class` 内共享，只在 table header 保存一次；
4. 首次及后续调用直接使用 compact metadata，不在首调重新创建 `NapiFunctionInfo`；
5. GC 对象、属性值和调用目标均保持当前 eager 形态，因此不引入 `InternalAccessor`、recipe directory、IC 失效或 slot 写回。

这不是“未调用时零 native metadata”，而是“**避免 N 个完整 per-function native allocation，用一块 compact table 替代，并把 metadata 解析推迟到真实调用**”。若目标必须是未调用函数完全不保留 `{callback, data}`，在现有 NAPI descriptor lifetime 下不可实现。

## 2. 为什么选择 D1

### 2.1 与 `06` 主方案的差异

`06` 的 C2 主方案在 prototype slot 中安装专用 lazy value，首次读取时创建 `JSFunction + JSNativePointer + NapiFunctionInfo`。它需要解决 key-aware property lookup、descriptor 伪装、HClass/LayoutInfo 原槽写回、IC 失效、新 GC 类型、snapshot 和 environment lifetime guard。

D1 不改变 JavaScript 对象图：

```text
当前与 D1 共同保持：
  prototype.slot[i] -> JSFunction -> JSNativePointer

当前 native metadata：
  JSNativePointer.Data -> 独立 NapiFunctionInfo

D1 native metadata：
  JSNativePointer.Data -> NapiCompactCallbackEntry
                           |
                           +-> table header { env, scopeId, liveRefs, entryCount }
```

因此 D1 不依赖“方法是否被读取”；任何目标函数在整个生命周期中都使用 compact metadata。

### 2.2 备选方案比较

| 方向 | 冷态 native 分配 | 首次调用分配 | 语义/修改面 | 结论 |
|------|------------------|--------------|-------------|------|
| C2：首次属性读取物化整个函数图 | recipe、directory、lifetime | 创建完整函数图 | property/IC/GC/snapshot 全链修改 | 保留为 `06` 主方案，不是本次最窄方向 |
| B1：只延迟 `NapiFunctionInfo`，首调创建并回写 | 仍需保存等价 cold record | 创建 `NapiFunctionInfo` | 有首调分配、回写和竞态；old+new metadata 可同时驻留 | 否决 |
| B2：复用 `JSNativePointer` 两个指针槽，冷态零分配 | 无 | 可选创建 | 无法同时保存 callback、data、env、scopeId；同 VM 可有多个 env | 通用场景不可行 |
| B3：完整 `NapiFunctionInfo` 按类 arena 分配 | 一块 arena | 无 | 分配次数减少，但结构字节不减少 | 仅适合作为生命周期 PoC |
| **D1：compact table** | **每类一块连续表** | **无** | **统一 callback 前缀和一个只读 VM 查询** | **选择** |

## 4. 不可能推迟的数据

| 数据 | 注册期来源 | `napi_define_class` 返回后能否无状态恢复 | D1 处理 |
|------|------------|-------------------------------------------|---------|
| `callback` | `napi_property_descriptor.method` 或 constructor callback | 不能；调用方 descriptor 可位于栈上 | 每 entry 复制 8 B |
| user `data` | descriptor/constructor data | 不能 | 每 entry 复制 8 B，非拥有 |
| `env` | `napi_define_class(env, ...)` | 不能由 VM 唯一恢复；同一 VM 可有 root/context env | table header 保存一次 |
| `scopeId` | 注册时 container scope | 不能用调用时 scope 替代 | table header 保存一次 |
| property key/name | 已进入 VM String 和函数 name | 已由当前对象图保存 | D1 不复制 |
| W/E/C attributes | LayoutInfo/PropertyAttributes | 已保存 | D1 不复制 |

同一次 `napi_define_class` 创建的 constructor 和 properties 共享 env 与注册时 scopeId，因此按类合并存在真实结构冗余可消除。

## 5. 最终数据结构

首版选择 E-24，避免让 NAPI callback dispatch 依赖新的 `JsiRuntimeCallInfo::GetExternalPointer()` ABI。legacy info 与 compact entry 显式共享 `{callback, data}` 前缀；每 entry 再用回指针取得 table header：

```cpp
struct NapiCallbackPrefix {
    NapiNativeCallback callback = nullptr;
    void *data = nullptr;
};

struct NapiFunctionInfo {
    NapiCallbackPrefix prefix;
    bool isSendable;
    napi_env env;
#ifdef ENABLE_CONTAINER_SCOPE
    int32_t scopeId;
#endif
};

struct NapiCompactCallbackTable;

struct NapiCompactCallbackEntry {
    NapiCallbackPrefix prefix;
    NapiCompactCallbackTable *table;   // non-owning; protected by liveRefs
};

struct NapiCompactCallbackTable {
    napi_env env;                      // non-owning, same lifetime contract as today
    int32_t scopeId;                   // registration-time snapshot, -1 when disabled
    uint32_t entryCount;               // number of allocated table entries
    std::atomic<uint32_t> liveRefs;    // one ref per published JSNativePointer
    // 紧随 header 的 entryCount 个 entries 由 Entries(table) 做 checked pointer arithmetic 取得。
};
```

`NapiCallbackPrefix` 只把现有头两个字段收拢为第一个 member，不改变它们的顺序、offset 或公开 NAPI ABI。两个 outer struct 与首 member 指针可互相转换；调用方必须通过 helper 取得 prefix，不能依赖非标准布局继承或违反 aliasing 规则。实现必须增加：

```cpp
static_assert(sizeof(NapiCallbackPrefix) == 2 * sizeof(void *));
static_assert(std::is_standard_layout_v<NapiCallbackPrefix>);
static_assert(std::is_standard_layout_v<NapiFunctionInfo>);
static_assert(std::is_standard_layout_v<NapiCompactCallbackEntry>);
static_assert(offsetof(NapiFunctionInfo, prefix) == 0);
static_assert(offsetof(NapiCompactCallbackEntry, prefix) == 0);
static_assert(offsetof(NapiCallbackPrefix, callback) == 0);
static_assert(offsetof(NapiCallbackPrefix, data) == sizeof(void *));
```

AArch64 设计大小仍为：legacy info 32/40 B、header 24 B、entry 24 B。实际实现用 checked size arithmetic 计算：

```text
table_bytes = align8(sizeof(header) + N * sizeof(entry))
```

必须检查 `N <= (SIZE_MAX - sizeof(header)) / sizeof(entry)`，分配失败时不得发布任何 compact entry。

### 5.1 为什么首版不用 E-16

E-16 去掉 entry 的 `table*`，改用 `JSNativePointer.ExternalPointer` 保存 table pointer，可把每函数 24 B 降到 16 B。它需要新增 `JsiRuntimeCallInfo` 读取同一 extra info `ExternalPointer` 的接口，并逐项证明 DFX、dump、serializer 和其他函数来源不会误解该字段。

E-16 是后续优化，不进入首版主方案。首版只要求一个 `FunctionRef` 只读接口判断当前 function 的 native entry/trampoline 类型，用于 `napi_call_function` 安全选择 metadata 解释器；不改变任何对象布局。

## 6. 注册与发布

### 6.1 Eligibility

只有同时满足以下条件时使用 compact table：

1. 普通、非 Sendable `napi_define_class`；
2. constructor callback 非空；
3. constructor 加目标 `property.method` 的总数足以覆盖 24 B header；
4. getter/setter、static method、value property 和非 method descriptor 继续走现有路径；
5. `napi_create_function` 继续使用 `NapiFunctionInfo`，因为其创建路径的 `JSNativePointer.ExternalPointer` 已保存 native callback；
6. 任何 checked-size、allocation 或 class creation 失败均整类回退/失败，不能混用半张 table。

首版只合并 constructor 与 prototype methods。static methods 可在实测证明同一 lifetime 和收益后纳入；getter/setter 保持 eager，避免扩大 callback kind 与 property 分支测试面。

### 6.2 阈值

设目标函数数为 `N`，基线每函数 requested bytes 为 `B`，首版 entry 为 `E=24 B`，header 为 `H=24 B`：

```text
requested_saving(N) = N * B - (H + N * E)
                    = N * (B - E) - H
```

requested-byte 正收益阈值：

| 基线 | 条件 | 最小 N |
|------|------|-------:|
| 32 B | `8N - 24 > 0` | 4 |
| 40 B | `16N - 24 > 0` | 2 |

正式 eligibility 不能只用 requested bytes；必须用目标 allocator 的 `malloc_usable_size` 或等价 probe 生成 actual-size 表，再按当前构建配置选择阈值。若无法得到稳定 actual-size，默认 `N >= 4`，并把 32 B 口径作为保守准入。

### 6.3 Two-phase publish

```text
1. 扫描 descriptors，计数 `1 + 目标 prototype methods`；checked 计算 N，其中 1 是 constructor。
2. 若未过阈值，走完整现有 eager 路径。
3. 分配一块 table，写入 env/scopeId，并为全部 N 个 entries 预留 `liveRefs=N`。
4. 填 constructor entry 和 method entries，但尚不让 GC 对象引用它们。
5. 按现有路径创建 constructor/method JSFunction + JSNativePointer。
6. 每成功安装一个 compact `JSNativePointer`，对应 reservation 转移给该对象，不修改 liveRefs。
7. class/prototype 成功创建后返回。
```

异常与失败处理：

- table allocation 或 checked-size 失败：优化回退到完整现有 eager 路径；不得发布 compact 状态；
- entry 已填但未发布：注册路径通过与 deleter 相同的 `ReleaseCompactTableRef` 释放该 reservation；不能绕过 refcount 直接 free；
- 部分函数已发布、后续 class creation 失败：注册路径只释放未发布 entries 的 reservations；临时函数由 handle/GC 路径终结并逐一释放已转移的 refs；
- `liveRefs` 从 N 开始，避免 function/extra-info 创建中的 GC 看见已引用但 refcount 仍为 0 的 table；
- 失败路径必须记录 reservation 是否已转移，保证每个 entry 恰好释放一次；
- constructor 也使用 compact entry，避免继续单独保留一份 32/40 B `NapiFunctionInfo`。

## 7. 调用协议

为 compact entry 使用独立 trampoline `ArkCompactNativeFunctionCallBack`，不在同一个 callback 内猜测 `Data` 的实际类型。

```text
JS call
  -> ArkCompactNativeFunctionCallBack(runtimeInfo)
  -> entry = runtimeInfo->GetData()
  -> table = entry->table
  -> validate table/entry relationship (debug/hardened build)
  -> env = table->env
  -> callback = entry->callback
  -> 保持当前 profiler、mixed-debug、critical-scope 和 exception 路径
  -> callback(env, runtimeInfo)
```

`napi_get_cb_info` 当前只从 `JsiRuntimeCallInfo::GetData()` 取 user data。D1 将 legacy info 与 compact entry 都解释为 `NapiCallbackPrefix*`，直接读取共同的第二字段：

```text
NapiCallbackPrefix *prefix = GetNapiCallbackPrefix(info->GetData());
userData = prefix->data;
```

`ArkNativeEngine::GetNativePtrCallBack(void *data)` 同样只读共同前缀的 `callback`，不需要增加第二套 DFX getter。

只有 `napi_call_function` 的 container scope 分支需要区分完整 legacy info 与 compact entry。新增一个通用、只读的 `FunctionRef::GetNativeEntryPoint(vm)`（名称可按现有 API 规范调整），返回函数现有的 native entry pointer；NAPI 层据此选择：

```text
compact target -> entry->table->scopeId
legacy target  -> NapiFunctionInfo->scopeId
```

不得用 `Concurrent::YES` 或 `IsConcurrentFunction()` 代替 metadata kind 判断。

不能靠 `Concurrent::YES`、magic value 或越界读取未知结构来判断 metadata kind。只读 entry-point 查询不得暴露 NAPI 私有类型，也不得改变 `JSFunction`/`Method` 布局。

## 8. Owner、释放与 teardown

### 8.1 Owner

- table allocation 的逻辑 owner 是其所有已发布 `JSNativePointer` 的集合；
- 每个 compact `JSNativePointer` 持有一个 `liveRefs` 引用；
- entry 不单独分配和释放；
- user `data`、callback code 和 `env` 仍遵循现有 NAPI lifetime，不由 table 释放。

### 8.2 Deleter

compact entry 使用独立 deleter，并与注册失败路径共用同一个 release helper：

```cpp
void ReleaseCompactTableRef(NapiCompactCallbackTable *table)
{
    if (table->liveRefs.fetch_sub(1, std::memory_order_acq_rel) == 1) {
        std::atomic_thread_fence(std::memory_order_acquire);
        FreeCompactTable(table);
    }
}

void CompactCallbackEntryDeleter(void *, void *, void *data)
{
    auto *entry = static_cast<NapiCompactCallbackEntry *>(data);
    ReleaseCompactTableRef(entry->table);
}
```

GC 可把 concurrent native callbacks 投递到 taskpool：

- `arkcompiler/ets_runtime/ecmascript/mem/heap-inl.h:1687-1701`
- `arkcompiler/ets_runtime/ecmascript/mem/heap.cpp:3209-3240`

因此 `liveRefs` 必须为原子；最后释放者可能不是 VM owner thread。table 不得依赖已经析构的 `NativeEngine` allocator、锁或 intrusive list。首版使用进程级可跨线程 free 的同一 allocator 对分配/释放配对。

### 8.3 不新增 engine registry

不建立 engine 级 table 登记链，也不在 environment teardown 提前释放 table。原因：

1. 现有 `NapiFunctionInfo` 同样由 `JSNativePointer/CommonDeleter` 最终释放；
2. table header 保存的 env 是 non-owning，与当前语义一致；
3. 提前释放会与延迟/并发 finalizer 竞争并造成 UAF；
4. 引用计数归零自然覆盖正常 GC、部分注册失败和 VM teardown；若内部调用者替换 function extra info，旧 wrapper 的 deleter 同样只释放其原有 table ref。

VM teardown 的现有顺序为 `EcmaVM::~EcmaVM -> ClearBufferData -> Heap::ClearNativePointerList`，后者对普通和 concurrent native-pointer lists 均调用 `JSNativePointer::Destroy`，随后 VM 才执行 `Heap::WaitAllTasksFinished`（`ecma_vm.cpp:570-587`、`:1041-1048`；`heap-inl.h:1835-1844`；`heap.cpp:2804-2813`）。因此 compact deleter 在 VM teardown 中仍有执行路径，D1 不需要 engine registry 抢先释放 table。

该顺序仍需 teardown DT/LSan 验证；若目标分支或平台存在绕过 `ClearNativePointerList` 的销毁路径，则保持 legacy fallback，不能用提前 free 修补。

### 8.4 `FunctionRef::SetData` 边界

`FunctionRef::SetData` 会新建一颗 `JSNativePointer` 并替换 function extra info（`jsnapi_expo.cpp:4450-4460`、`js_function.cpp:1109-1140`），但不会同步替换该函数的 native trampoline。因此：

- legacy NAPI 函数被替换后，新 data 仍必须满足 `ArkNativeFunctionCallBack` 的 `NapiFunctionInfo` 契约；任意 data 在当前基线同样会类型错配；
- compact NAPI 函数被替换后，新 data 必须满足 `ArkCompactNativeFunctionCallBack` 的 compact-entry 契约，并持有有效 table ref；
- 两个目标仓的生产代码扫描未发现注册后对 native NAPI class method 调用 `FunctionRef::SetData`；现有 ArkUI NAPI 使用点 `FunctionSetContainerId` 会先排除 native function（`ark_native_engine.cpp:152-186`）；
- D1 不修改这个通用内部 API，也不承诺“任意 SetData 后仍可调用”。测试只验证旧 wrapper 被替换后会准确 release 一次；若未来出现生产调用者，必须通过 NAPI 私有 helper 安装完整 compact entry，而不是直接写任意 data。

### 8.5 动态库卸载边界

table 只复制 callback 地址，不拥有或 pin 动态库，和当前 `NapiFunctionInfo` 一致。当前 module deregister 可在注册计数归零后尝试卸载，module manager 最终调用 `dlclose`（`arkcompiler/ets_runtime/ecmascript/module/js_module_deregister.cpp:159-188`；`foundation/arkui/napi/module_manager/native_module_manager.cpp:241-266`、`:1329-1343`）。若函数逃逸到 module graph 外并在 SO 卸载后继续调用，callback 地址可能失效，这是现有 eager 路径同样存在的生命周期风险。

D1 不新增 module pin/refcount，不声称修复 unload 安全。发布测试必须验证 D1 与 legacy 的 module unload 行为一致；若产品要求 escaped callback 在 unload 后仍可调用，需要另立 module lifetime 方案，其成本不得计入 D1。

### 8.6 Exactly-once 与失败

D1 不在首次调用做分配或状态切换，因此没有首调 exactly-once 发布、等待者、失败重试或半初始化 handle。

唯一全局 exactly-once 操作是最后一个 release 释放 table，由 `fetch_sub == 1` 保证。每个 entry reservation 必须恰好走“转移给 JSNativePointer 后由 deleter release”或“未发布时由注册失败路径 release”之一。必须断言：

- `liveRefs` 不会从 0 递减；
- 同一 `JSNativePointer` 的 deleter 最多调用一次；
- entry pointer 位于 `[entries, entries + entryCount)`；
- entry->table 与 deleter 的 owner 一致；
- callback 调用期间函数对象保持可达，deleter 不与在途调用释放同一 entry。

## 9. 保持不变的语义

| 面 | D1 行为 |
|----|---------|
| public NAPI ABI | 不变 |
| `napi_property_descriptor` | 不变；仍只在 `napi_define_class` 注册调用内读取，不延长调用方 descriptor lifetime |
| JSFunction identity/name/length | 不变；注册期按现有路径创建 |
| prototype property descriptor | 不变；仍是普通 data property |
| HClass/LayoutInfo/property offset | 不变 |
| property read/write/delete/freeze/seal | 不变 |
| interpreter/IC/AOT/MegaIC | 不改 |
| GC object layout/visitor/verifier | 不改 |
| snapshot/serializer | 不增加 GC 类型或 native pointer 字段 |
| `JSNativePointer` layout | 不改；Data 仍为 native pointer |
| Sendable | 保持 legacy `NapiFunctionInfo` |
| multi-VM/multi-context | 每 table 保存准确注册 env，不由 VM 反推 |
| container scope | header 保存注册时 scopeId，`napi_call_function` 按 compact kind 读取 |

D1 改变的是 NAPI 私有 native metadata 表示和内部 trampoline，不改变 JS 调用协议、参数栈或 `napi_callback_info` 公开含义。

## 11. 收益模型

### 11.1 单类 requested bytes

设一个 eligible class 有 `N` 个 compact 函数，含 constructor 与目标 prototype methods：

```text
current_requested(N) = N * B
D1_requested(N)      = H + N * E
requested_saving(N)  = N * (B - E) - H
```

首版 AArch64 参数：

```text
B = 32 B（无 container scope）或 40 B（启用 container scope）
E = 24 B
H = 24 B
```

所有函数都会保留 table entry，因此 D1 收益不依赖读取或调用比例。它是 native shallow/requested-byte 降低和 allocation-count 降低，不是 GC shallow heap 收益。

### 11.2 allocation count

对一个含 `N` 个目标函数的类：

```text
current: N 次 NapiFunctionInfo allocation
D1:      1 次 compact table allocation
减少:    N - 1 次 allocation
```

`JSFunction` 和 `JSNativePointer` allocation count 不变。

### 11.3 默认同生存与非默认部分存活

`napi_define_class` 注册本身没有按方法注销或释放动作，函数被调用也不会改变其可达性。当前对象图为：

```text
class constructor -> prototype
prototype -> constructor property -> class constructor
prototype -> method property slots -> all registered method JSFunctions
```

源码中，class function 保存 prototype（`js_function.cpp:153-170`）；prototype 的 `constructor` slot 回指 class function，并写入全部 method values（`jsnapi_class_creation_helper.cpp:78-146`）。因此在不修改属性图的普通使用中，只要 class constructor 或 prototype 任一仍可达，本表纳入的 constructor 和全部 prototype methods 都可达，`L=N`。ArkNativeEngine 还把 module exports 保存为 `Global<JSValueRef>` cache（`ark_native_engine.cpp:835-903`、`:1055-1093`），通常进一步延长导出 class graph 的整体生命周期。

独立 `NapiFunctionInfo` 可能单个回收，仅发生于注册后的非默认图变异：

1. `C.prototype.m = replacement`、`Object.defineProperty(C.prototype, "m", ...)` 或 `delete C.prototype.m` 单独移除旧 method；旧函数没有其他引用时可被 GC 单独回收；
2. native/framework 代码通过等价 NAPI property API 覆盖或删除某个 prototype method；
3. 代码先保存 `const f = C.prototype.m`，随后从 exports 删除 class 或让原 class/prototype graph 整体不可达，仅 `f` 继续存活；
4. host 内部调用 `FunctionRef::SetData` 替换某个函数的 extra info，使旧 `JSNativePointer` 单独进入 finalizer 路径。

这些操作能否发生取决于 descriptor 的 W/C 位，而不是 `napi_define_class` 固有行为：

- OpenHarmony `DECLARE_NAPI_FUNCTION` / `DECLARE_NAPI_FUNCTION_WITH_DATA` 宏只设置 `napi_writable`，所以赋值或满足约束的 `defineProperty` 可替换旧函数，但 `delete` 不成功（`interfaces/inner_api/napi/native_common.h:97-119`）；
- 标准 `napi_default_method` 是 writable + configurable，可替换也可删除（`interface/sdk_c/third_party/node/src/js_native_api_types.h:30-43`）；
- `napi_default` 不含 W/E/C，普通 JavaScript 代码不能替换或删除该 method；
- 若具体 method 不可写且不可配置，则前两类用户操作不能移除旧函数。

GC 只在 old/full GC 发现某个 `JSNativePointer` 不可达后调度 deleter（`heap-inl.h:1662-1701`）；不存在“调用完某方法就释放 metadata”的路径。

连续 table 的边界是 entry 不能单独归还 allocator。仅在上述非默认图变异后，才可能出现注册时 `N` 个 entries、检查点仅剩 `L` 个原始函数存活：

```text
legacy_live_requested(L) = L * B

D1_live_requested(N, L) = 0,                 L = 0
                          H + N * E,          0 < L <= N

checkpoint_saving(N, L) = legacy_live_requested(L)
                          - D1_live_requested(N, L)
```

当 `0 < L << N` 时，一条被提取的方法引用可能钉住整表，阶段性成本可高于 legacy。但这不是普通 NAPI 注册生命周期，也不依赖方法是否被调用；它是 prototype/class 图被后续改写后的兼容性边界。

验证要求：默认注册场景按 `L=N` 计算；另外用“覆盖一个 method”“覆盖 N-1 个 methods”“仅保留一个 extracted method”三个对抗用例确认正确释放并量化 pinned bytes。该边界不作为否决 D1 的默认前提，是否需要 chunk table 由真实 workload 中属性改写率与 pinned actual bytes 决定。

### 11.4 Top13 条件上界

冻结 evidence `evidence/top13-native-interop-method-census.json` 给出：

- method unique closure population：447,707；
- constructor population：57,737；
- `c_protos` 合计：64,392。

该证据按快照对象关系分桶，不是按 `napi_define_class` 创建路径得到的 eligible property-slot census。不能直接把全部 447,707 当成 D1 可改 entry 数，也不能证明每个 `c_proto` 对应一张目标 table。

若仅用于条件模型，假设 `M=447,707` 全部是 eligible method，`C=64,392` 张表，每表 header 24 B，且 constructor 不计入 entry（保守、不申领 constructor 收益）：

```text
32 B baseline:
  M * (32 - 24) - C * 24
  = 2,036,248 B
  = 1.942 MiB

40 B baseline:
  M * (40 - 24) - C * 24
  = 5,617,904 B
  = 5.358 MiB
```

这只是**带 header 抵扣的结构条件上界**，不是承诺收益。正式数字必须通过创建侧插桩获得每类真实 `N`、table 数、legacy fallback 数和 actual allocation bytes。

### 11.5 不得计入的收益

- 不把 `JSFunction` 或 `JSNativePointer` 计入 D1 收益；二者仍创建；
- 不把 C2 将来可避免的 recipe/directory 算作 D1 收益；
- 不把 malloc 头部假定为固定 8/16 B；必须测 actual/usable；
- 不把 requested bytes 等同于 committed、RSS 或 PSS；
- 不把 snapshot unique closure population 当成创建路径已验证的 entry 数；
- 不把 constructor 或 static/getter/setter 计入，除非实现实际纳入且插桩证明。
- 不把 table 内已死亡但尚未物理释放的 entry 从 live bytes 中扣除。

## 12. 风险与控制

| 风险 | 控制 |
|------|------|
| compact/legacy data 类型混淆 | 使用独立 trampoline；按 Function native pointer/kind 分支，不使用 magic 字段猜测 |
| `Concurrent::YES` 误判函数 kind | 禁止用它判断 metadata；DT 覆盖普通 method 的 `IsConcurrentFunction=false` |
| scopeId 语义变化 | table header 固化注册时 scopeId；root/context + container-scope 对照 |
| env 错配 | header 保存原始注册 env；不从 `JSNApi::GetEnv(vm)` 恢复 context env |
| 最后释放并发 | atomic `liveRefs` + acq_rel；ASan/TSan/LSan 和 finalizer taskpool 压测 |
| 部分注册失败泄漏/双释放 | two-phase publish；`liveRefs=N` 预留全部 entry reservations，逐项记录“已转移给 wrapper”或“失败路径释放”，故障注入验证恰好一次 |
| `FunctionRef::SetData` 替换 extra info | 不是公开 NAPI 语义；新 data 必须匹配既有 trampoline 类型，旧 wrapper 只验证恰好 release 一次 |
| module unload 后 callback 地址失效 | table 不拥有 SO，维持 legacy lifetime；不申领 unload 修复，escaped callback 的 module pin 另案评审 |
| user data 所有权误判 | entry 只复制指针，不释放 `data` 目标 |
| table 大小溢出 | checked multiply/add；oversize 保持 legacy 或按当前 API 报错 |
| callback/data prefix 漂移 | `offsetof`/`sizeof` 静态断言；legacy/compact 混合调用与 DFX 用例 |
| 单方法/小类负收益 | actual-size 准入阈值；默认保守 N>=4 |
| 非默认属性改写使少量原函数钉住整表 | 默认对象图按 `L=N`；覆盖/删除/extracted-method 对抗用例分列 `N/L` 与 pinned bytes，不把该边界误写成调用触发的常规回收 |
| RSS/PSS 无可见收益 | clean A/B 分开报告 requested/usable/RSS/PSS，不把结构值冒充物理收益 |

## 13. 测试与验证

### 13.1 ABI 与 allocator

- AArch64 build 中 `static_assert(sizeof(NapiCompactCallbackEntry) == 24)`；
- `static_assert(alignof(...) == 8)`；
- 对 32/40 B legacy allocation 与 `H+24N` table 测 `malloc_usable_size`/等价接口；
- `N=1..16` 输出 requested、usable、allocation count，生成 eligibility threshold；
- 32/64 位目标分别验证，不把本次 AArch64 probe 外推到所有 ABI。

### 13.2 功能与协议

- constructor 和 4/8/32 个 prototype method 正常调用；
- 每个 method 的 callback、user data、name、length、this、args、newTarget 与 legacy 对照；
- `napi_get_cb_info(..., &data)` 返回对应 entry 的 user data；
- JavaScript 直接调用与 `napi_call_function` 均覆盖；
- profiler、mixed debug、critical scope、exception、pending exception 与 legacy 对照；
- getter/setter/static/value/Sendable/`napi_create_function` 均走 legacy；
- compact 与 legacy 函数混合存在时不误解 metadata。

### 13.3 生命周期

- 默认 class/prototype 对象图整体可达、整体不可达时，table 在最后一个 deleter 后释放；
- 覆盖一个 method、覆盖 N-1 个 methods、仅保留一个 extracted method 的非默认部分存活场景；
- partial allocation/class creation failure 的 liveRefs 与 free 次数；
- 用 compact-compatible entry 替换 extra info，验证旧 wrapper 恰好 release 一次；任意 data 类型错配不是 D1 支持场景；
- module unload/worker teardown 与 legacy 行为对照，不把 callback module pin 计入 D1；
- minor/full/compact GC、concurrent finalizer、VM teardown、worker teardown；
- root env、多 context env、多 VM 同时存在；
- ASan/LSan 必须无 UAF、double free 和 leak；支持时以 TSan 验证 liveRefs。

### 13.4 clean A/B

同一源码基线、产品、编译参数、bundle、操作序列和采样点，分列：

- `napi_define_class` 调用数、每类目标 N、fallback 数；
- legacy `NapiFunctionInfo` allocation count/requested/usable；
- compact table allocation count/requested/usable；
- 注册耗时、callback P50/P95/P99 和稳态吞吐；
- native heap committed/fragmentation、进程 RSS/PSS；
- JS heap shallow/committed 与 GC pause 作为不应显著变化的对照指标。

只有冷启动和后台 clean A/B 都无回归，且 native usable/物理指标有可重复下降，才扩大默认启用范围。

## 15. 最终判断

D1 是当前可选择的最窄 native-only 次方向：

- 保持 `06` 所关心的 GC 对象布局、ABI、snapshot、property descriptor 和调用栈参数协议不变；
- 不修改属性读取、InternalAccessor、IC、HClass/LayoutInfo 或 GC；
- 将每函数独立 32/40 B `NapiFunctionInfo` 和对应 allocation 改成每类一块 24 B header + 24 B/entry 的 native table；
- 把 env/scope/callback metadata 的解析推迟到真实调用，但不在首调分配或回写；
- 对小类按 allocator actual 回退 legacy，避免 header 抵消收益；
- 用现有 JSNativePointer finalizer 生命周期和 table 原子引用计数完成释放，不新增 engine registry 或 teardown side table。

它不能消除调用方必须在注册期交付的 `{callback, data}` 16 B，也不减少 JS heap；其价值是以显著更小的修改面减少 native allocation 次数、requested/usable bytes 和 allocator 碎片。是否形成 RSS/PSS 收益必须由实现后的 clean A/B 证明。
