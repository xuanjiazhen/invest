# Native Interop 闭包惰性原型绑定 —— 背景

本文件存放理解本方案所需的背景知识与现有实现介绍。

## 1. 问题：native 类方法的即时绑定

ArkTS/NAPI 应用中，native 类通过 `napi_define_class` 注册。调用链：

```
napi_define_class                      native_api.cpp:1643
 └─ NapiDefineClass                   ark_native_engine.cpp:333
  └─ NapiCreateClassFunction      ark_native_engine.cpp:288
   └─ NapiGetKeysAndAttrsFromProps   ark_native_engine.cpp:250  ← 遍历 property_count
    └─ NapiInitAttrValFromProp   ark_native_engine.cpp:216
     └─ NapiNativeCreateFunction  ark_native_engine.cpp:190
      └─ FunctionRef::NewConcurrentWithName  jsnapi_expo.cpp:3947
```
```
napi_define_class                      native_api.cpp:1643
 └─ NapiDefineClass                   ark_native_engine.cpp:333
  └─ NapiCreateClassFunction      ark_native_engine.cpp:288
   └─ NapiGetKeysAndAttrsFromProps   ark_native_engine.cpp:250  ← 遍历 property_count
    └─ NapiInitAttrValFromProp   ark_native_engine.cpp:216
     └─ NapiNativeCreateFunction  ark_native_engine.cpp:190
      └─ FunctionRef::NewConcurrentWithName  jsnapi_expo.cpp:3947
```

`napi_define_class` 在类定义时**即时**为 prototype 上每个方法创建 JSFunction，与该方法的访问/调用、类是否被实例化无关。

## 2. 单个 native 方法的实际开销

| 项 | 位置 | 大小 | 是否共享 |
|----|------|------|---------|
| `NapiFunctionInfo` | `new`（native_value.h:54） | 32 B（容器场景 40 B） | 否，堆外 |
| 方法名 `EcmaString` | 字符串表 | — | 是（intern） |
| 函数 hclass | transition 查找 | 88 B | 是（每 context 一份） |
| JSFunction | `NewNativeFunctionByHClass` | 112/136/144 B | 否 |
| `JSNativePointer` | `SetFunctionExtraInfo` | 40 B | 否（HashField 1:1 独占） |

每个未被访问的 native 方法驻留成本：**堆内约 144 + 40 = 184 B，堆外 32–40 B + malloc 记账**。

## 3. Top13 目标存量（Bucket C）

快照检出 959,398 个共享同一 native Method stub 的 JSFunction（128.22 MiB，占堆 7.78%）。按持有方式分桶：

| Bucket | 描述 | 节点数 | MiB |
|--------|------|--------|-----|
| A | 匿名 accessor 绑定（getter/setter） | 265,645 | 32.96 |
| B | 命名方法，prototype 持有，类有存活实例 | 25,977 | 3.56 |
| **C（方法分量）** | **普通/命名方法，prototype 持有，类零实例** | **447,707** | **61.474** |
| D | 命名方法，非 prototype 持有 | 220,069 | 30.22 |

完整 Bucket C 还包含上述零实例类对应的 constructor 闭包 57,737 个、7.062 MiB；合计 505,444 个、68.536 MiB。本方案 A2 只改 prototype 方法 slot，直接目标是 Bucket C 的**方法分量** 447,707 个、61.474 MiB，constructor 必须单列，不能把 61.47 MiB 称作完整 Bucket C。

## 4. 收益口径：61.47 MiB 方法分量是上界而非期望值

「零实例类」是「方法从未被访问」的**代理指标**，不是同一件事：

- **高估方向**：类零实例但 prototype 方法被读取（能力探测、方法包装/埋点、`Object.getOwnPropertyNames` 后取值、桥接层自动绑定、`Object.freeze`、浅拷贝、调试序列化）——惰性 slot 会被 materialize，收益为零；
- **低估方向**：类有实例但大部分方法未被调用（Bucket B 全量仅 3.56 MiB，构成低估上界）。

91.0% 的零实例原型（4,391/4,827）其类对象已暴露在 JS 可达图中，不存在「JS 拿不到该类」的结构性免疫。期望收益需插桩统计「从未被读取的方法占比」后折算。

## 5. VM 已有惰性机制：InternalAccessor（方案 A 的复用底座）

VM 对内建对象（Date/Set/Map/WeakMap 等）已有一套**惰性初始化**机制：启动时全局对象上不驻留完整内建对象，只装一个 24 B 的 `InternalAccessor` 占位，首次访问才真正构建。本方案（惰性原型绑定）就是把这套机制的作用域从内建对象扩展到 NAPI 类。以下按真实源码拆解它的作用。

### 5.1 它是什么：两个裸函数指针的极小占位对象

`ecmascript/accessor_data.h:29-46`：

```cpp
class InternalAccessor final : public Record {
    using InternalGetFunc = JSTaggedValue (*)(JSThread *, const JSHandle<JSObject> &);   // getter 裸指针
    using InternalSetFunc = bool (*)(JSThread *, const JSHandle<JSObject> &,
                                     const JSHandle<JSTaggedValue> &, bool);             // setter 裸指针
    static constexpr size_t GETTER_OFFSET = Record::SIZE;          // 8 B
    ACCESSORS_FIXED_SIZE_FIELD(Getter, InternalGetFunc, JSTaggedType, GETTER_OFFSET, SETTER_OFFSET)
    ACCESSORS_FIXED_SIZE_FIELD(Setter, InternalSetFunc, JSTaggedType, SETTER_OFFSET, SIZE)  // 共 24 B
    DECL_VISIT_NATIVE_FIELD(GETTER_OFFSET, SIZE)   // native 字段：GC 不扫描、无堆引用
};
```

要点：它**不是 JSFunction**——没有对象头之外的任何 JS 语义（无 name/length/prototype），只是「getter/setter 两个 C 函数指针 + 一个可空 payload 位」。这是它能做到 24 B、且不进 IC/GC 复杂路径的原因。

### 5.2 它怎么用：以 `Date` 为例的完整生命周期（真实源码）

**① 启动时安装占位**（`builtins.cpp:1078-1087`，`LazyInitializeDate`）：

```cpp
JSHandle<JSTaggedValue> key(factory_->NewFromUtf8ReadOnly("Date"));
auto accessor = factory_->NewInternalAccessor(
    nullptr,                                        // setter = nullptr（getter-only）
    reinterpret_cast<void *>(BuiltinsLazyCallback::Date));  // getter = 专属静态回调
SetLazyAccessor(globalObject, key, accessor);       // DefineOwnProperty 装成 accessor 属性
```

此刻 `globalThis.Date` 槽位指向 24 B accessor——Date 构造函数/原型/全部方法对象**尚未创建**。

**② 首次读取触发回调**（属性查找分发，`object_fast_operator-inl.h:1080-1082`）：

```cpp
if (UNLIKELY(accessor->IsInternal())) {
    return accessor->CallInternalGet(thread, objHandle);   // 调用裸 getter
}
```

对应 JS 侧行为：

```js
typeof Date;   // 首次：命中 accessor → CallInternalGet → BuiltinsLazyCallback::Date
typeof Date;   // 再次：槽位已是数据属性，直接命中构造函数
```

**③ 回调构建真身并物化写回**（`builtins_lazy_callback.cpp:23-36`）：

```cpp
JSTaggedValue BuiltinsLazyCallback::Date(JSThread *thread, const JSHandle<JSObject> &obj)
{
    ResetLazyInternalAttr(thread, obj, "Date");            // ① 先把槽位从 accessor 改回数据属性
    Builtins builtin(thread, factory, vm);
    builtin.InitializeDate(env, objFuncPrototypeVal);      // ② 真正构建 Date 构造函数/原型/方法
    return env->GetDateFunction().GetTaggedValue();        // ③ 返回真身作为本次读取结果
}
```

物化写回 `ResetLazyInternalAttr`（同文件）：fast 模式下定位 Layout 条目后 `attr.SetIsAccessor(false)` 原地改 attr；字典模式改 NameDictionary。

### 5.3 对本方案的意义：能复用什么、不能平移什么

| 可直接复用 | 不能平移到 NAPI（差异详见 `06-InternalAccessor迁移NAPI设计评审.md` §2.3 D1–D4） |
|---|---|
| 「accessor 占位 → 首读分发 → 构建真身 → 写回数据属性」的物化范式 | **身份模型**：内建槽位的身份编码在「每槽一个专属静态函数」（Date 槽配 `::Date`），回调签名不收属性键；NAPI 方法运行期动态注册，必须给 accessor 加 payload（`NapiLazyAccessor`，32 B，06 §3.3 X1） |
| `CallInternalGet` 慢路径分发骨架（property lookup 对 internal accessor 已有分支） | **写回路径**：`ResetLazyInternalAttr` 原地改 attr 依赖全局对象槽位的私有存储；NAPI 目标是 prototype（共享 LayoutInfo + 原型链 IC），必须走 SetProperty 等价路径 + `MarkProtoChanged` 失效链（06 §4.3） |
| 注册期开关/回退形态 | **生命周期**：内建永不卸载、单线程；NAPI 有 module unload/worker/并发首访，需 per-slot 状态机与释放所有者（06 §4.5） |

一句话：InternalAccessor 证明了「占位 24 B + 首读物化」在 VM 内是成熟范式；本方案借它的骨架，把身份与写回两处按 NAPI 场景重造（设计见 06）。
