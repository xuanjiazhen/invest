# 对象字面量外置 Backing COW —— 方案设计

## 1. 问题与价值

对象字面量模板由 ConstantPool 持有。每次执行对象字面量时，ArkVM 当前创建新 `JSObject`，深拷贝模板的 `Elements`、`Properties`，并复制 inline properties。带 lexical environment 的路径还会克隆函数并重绑 `LexicalEnv` / `HomeObject`（`object_factory.cpp:498-536,603-673`；`compiler/new_object_stub_builder.cpp:226-303,332-445`）。

对于创建后未修改外置属性/元素的实例，深拷贝 backing 是重复分配和复制。本方案让满足白名单的模板 backing 直接使用 `COWTaggedArray`；克隆实例先共享，首次写入时再复制对应 backing。

## 2. 范围与兼容性

### 2.1 修改范围

- ConstantPool 对象字面量模板的外置 `Properties` / `Elements` 创建；
- Runtime 两个 `CloneObjectLiteral` 重载；
- `NewObjectStubBuilder::CloneObjectLiteral`；
- 普通 `JSObject` 的属性/元素写入、删除、扩容、dictionary 转换和 elements-kind migration；
- COW census、heap dump 标识和运行时开关。

### 2.2 不修改

- 数组字面量、字符串共享、HClass 共享、inline properties；
- abc/字节码、公开 API、对象头和 JSObject 布局；
- 跨 VM / shared heap 所有权；
- 含实例化函数或访问器的 backing。

关闭开关时走原深拷贝路径。COW 状态由 backing 的既有 `COW_TAGGED_ARRAY` HClass 表示，不新增 JSObject 字段。

## 3. 状态与不变量

每个 `Properties` / `Elements` backing 独立经历：

```text
template build
  ├─ ineligible --------------------------> ordinary backing / clone-by-copy
  └─ eligible -> COW backing
                    ├─ clone read --------> shared COW backing
                    └─ clone first write -> allocate ordinary backing
                                             copy all slots
                                             publish to owner with barrier
                                             perform write
```

必须始终满足：

1. COW backing 只读，任何原地 `Set` 前必须脱离。
2. 脱离以 owner `JSObject` 为单位，`Properties` 与 `Elements` 互不影响。
3. 新 mutable backing 完整初始化后才能发布到 owner；发布后再执行目标写入。
4. inline properties 始终属于实例，不参与共享。
5. 需要 `HomeObject` / lexical env 重绑的值仍按实例克隆。
6. COW backing 不跨 VM；普通对象线程安全语义不因本方案扩大。

## 4. 详细设计

### 4.1 模板 eligibility

对象字面量模板 materialize 时分别检查 `Properties` 和 `Elements`：

- 长度为 0：继续使用全局 `EmptyArray`，无优化动作；
- fast `TaggedArray`、长度不超过阈值、且无 `JSFunction` / `AccessorData`：直接分配或转换为本地 NON_MOVABLE `COWTaggedArray`；
- dictionary、超阈值、需实例化重绑或无法识别：保持普通 backing。

首版在模板创建阶段完成 eligibility，避免每次 clone 扫描全部槽位。阈值不沿用数组字面量的常量值，先由对象字面量 backing 长度、首次写率和碎片数据确定。

### 4.2 CloneObjectLiteral

Runtime 与 compiler stub 采用相同规则：

1. 新建独立 `JSObject`；
2. backing 为 `COWTaggedArray` 时直接安装到 clone；
3. 普通 backing 继续调用现有 `CloneProperties`；
4. inline properties 继续逐槽复制；
5. 含 `JSFunction` / `AccessorData` 的路径继续克隆并重绑；
6. `canShareHClass` 逻辑保持不变，与 backing COW 解耦。

### 4.3 写前脱离

新增 owner-aware 语义 helper，分别处理 `Properties` 和 `Elements`：

```text
EnsureMutableLiteralProperties(thread, object)
EnsureMutableLiteralElements(thread, object)
```

名称为设计示意，最终接口遵循源码命名。helper 仅在 backing `IsCOWArray()` 时：

1. 读取长度、extra length 和 elements kind；
2. 在当前 VM 本地 heap 分配对应普通 mutable backing；
3. 完整复制所有槽位；
4. 通过正确写屏障替换 owner 的 backing；
5. 返回 mutable backing。

必须覆盖的 owner-aware 写入口：

- 现有属性覆盖、添加、删除、`defineProperty`；
- fast properties 扩容及 fast/dictionary 双向转换；
- 数值 key 的元素写、删除与扩容；
- elements-kind migration；
- runtime stubs、IC store、AOT/compiler 直接写路径；
- debugger/反射和内部 helper 中可达的 backing 修改。

禁止仅在 `TaggedArray::Set` 内实现 COW：该接口不知道 owner，无法把复制后的 backing 发布回正确对象。

### 4.4 GC 与内存域

复用现有 `COWTaggedArray` 的 GC visitor 和 NON_MOVABLE 分配。模板与多个 clone 都是普通强引用；GC 只需按现有 tagged slots 扫描。首次写生成的 mutable backing 回到当前 VM 的普通分配策略。

首版不进入 shared heap，不处理跨 VM 引用，也不引入引用计数。NON_MOVABLE 碎片和 Region commitment 必须通过 clean A/B 测量；超过阈值的 backing 直接回退深拷贝。

### 4.5 Compiler/AOT 一致性

`NewObjectStubBuilder::CloneProperties` 当前会逐槽克隆函数并设置 `LexicalEnv` / `HomeObject`。compiler 路径只有在模板 backing 已被标记为 COW 时才能直接共享；否则保留现有循环。所有 store stub 必须执行与 runtime 相同的 `IsCOWArray` 检查，或在命中时调用统一 runtime 脱离入口。

不改变 AOT 文件格式。旧产物产生普通 backing 时自然走深拷贝；新 runtime 不得把未标记的 backing 推断为可共享。

### 4.6 回退与发布

增加产品开关，默认关闭。发布顺序：

1. census-only：仅采集 eligibility、长度、clone 和首次写；
2. debug/实验构建开启 COW，执行语义和 GC 压力测试；
3. 目标应用 clean A/B；
4. 只有事件净减少、full-GC shallow、Region committed 和 RSS/PSS 均无负向结论时才评估默认开启。

## 5. 收益模型

事件累计模型：

```text
avoidedCloneBytes = Σ(N_i × B_i)
detachCopyBytes    = Σ(W_i × B_i)
eventNetBytes      = avoidedCloneBytes - detachCopyBytes
```

快照时刻的 clone backing 浅层毛收益近似为 `Σ((L_i - M_i) × B_i)`，其中 `L_i` 是仍存活 clone 数，`M_i` 是已脱离 clone 数。该公式必须以插桩或 clean A/B 验证，不能从通用 `JSObject` 存量推导。

成本必须单列：COW 检查、首次写复制、NON_MOVABLE 碎片、额外 Region commitment、GC 扫描变化和峰值复制。shallow、committed、RSS/PSS 不互相替代。

## 6. DFX

- clone：总次数、COW 命中次数、Properties/Elements 长度与字节桶；
- fallback：empty、dictionary、oversize、function/accessor、unsupported kind；
- write：首次脱离次数、复制字节、写类型和 backing 类别；
- A/B：young/full GC 后 shallow、Region used/committed、峰值和稳态 RSS/PSS；
- heap dump：区分对象字面量模板 COW backing 与既有数组 COW backing。

详细打点见 `05-插桩patch.md`。

## 7. 关键测试

| 类别 | 场景 | 预期 |
|---|---|---|
| 只读共享 | 同一点位创建多个纯数据对象字面量 | 内部 backing 共享，JS 对象身份独立 |
| 属性首次写 | 修改已有属性、添加、删除、`defineProperty` | 仅目标实例脱离，其他实例与模板不变 |
| 元素首次写 | 数值 key 写入、扩容、删除、kind migration | 先脱离再写，值和 kind 正确 |
| 函数/访问器 | 方法、getter/setter、`super`、闭包捕获 | 回退深拷贝，`HomeObject` / lexical env 正确 |
| 属性语义 | symbol、descriptor、枚举顺序、冻结/密封 | 与关闭开关逐项一致 |
| 存储转换 | fast/dictionary、properties grow、elements grow | 无 COW 原地修改，无数据丢失 |
| 执行层 | interpreter、runtime stub、AOT | 结果和 COW 命中一致 |
| GC/DFX | young/full GC、heap dump、长循环 | 无悬垂/污染，统计守恒 |
| 回退 | 开关关闭、超阈值、unsupported kind | 完全使用原深拷贝路径 |

## 8. 工作量

设计 4 人日，开发 16 人日，测试 10 人日，总计 30 人日。2 名开发并行时预计第 4 周完成开发和功能验证，第 5 周完成 clean A/B、物理内存测量与评审闭环。

## 9. 结论

本方案只实现对象字面量外置 backing COW。可行性建立在两个门槛上：写路径完整覆盖，以及插桩证明未写 clone 足以抵消首次写复制和 NON_MOVABLE 成本。两项未满足前，方案保持默认关闭且不承诺净内存收益。
