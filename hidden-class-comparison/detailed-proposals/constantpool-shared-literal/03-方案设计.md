# ConstantPool 跨 VM 共享与字面量优化 —— 方案设计（按架构特性设计模板）

## 1、特性需求/问题/动机的来源与价值

**问题来源**：多 VM（主 + worker）加载同一 abc 时，unshared ConstantPool 的字符串条目在每 VM 字符串表重复 intern（随 VM 数线性重复）；字面量对象（Array/Object 字面量）每次创建执行 HClass 查找 + elements/properties 深克隆，对象字面量尚无数组字面量已有的 COW 优化。

**价值**：多 VM 场景下消除字符串常量的跨 VM 重复；降低对象字面量创建成本（时间 + 空间）。

**实现前 vs 实现后**：实现前每个 worker VM 各持一份 ConstantPool 字符串对象与对象字面量 backing；实现后字符串跨 VM 复用、对象字面量 backing COW 共享。

## 2、特性影响分析

### 2.1 系统位置

ConstantPool 对象层（字符串/字面量条目）+ 字符串表（EcmaStringTable）+ 字面量创建路径（ObjectFactory）+ shared heap。

### 2.2 环境依赖

- 子方向 A：shared heap 字符串支持（sendable 字符串已有）；多 VM/worker 场景；
- 子方向 B：read-only HClass、ENABLE_COW_ARRAY。

### 2.3 涉及模块

`ecma_string_table`、`ecma_vm`（字符串表归属）、`object_factory`（字面量创建/克隆）、`shared_object_factory`、GC（shared heap 遍历）、worker 生命周期。

### 2.4 前后版本兼容性

- 不改变字节码格式、公开 API、ConstantPool 布局；
- 字符串 intern 语义不变（=== 与去重行为一致）；
- 对象字面量创建结果语义不变（每次独立对象）。

### 2.5 外部用户感知

无（字符串去重、字面量语义与可见行为不变）。

### 2.6 性能影响

- 时间：字符串共享减少每 VM intern 成本（多 VM 场景）；对象字面量 COW 减少克隆成本（热路径）；
- 空间：多 VM 字符串对象线性重复消除；字面量 backing 共享。

## 3、业界竞品分析

| 引擎 | 做法 |
|---|---|
| V8 | 字符串表跨 isolate 不共享（isolate 私有），但共享内置/只读字符串（ReadOnlySpace）；对象字面量用 feedback 复用 shape |
| JSC | 字符串表按 VM 私有；对象字面量有结构缓存 |
| Hermes | 字符串驻留按 VM |
| ArkVM（本方案） | 多 VM 场景字符串跨 VM 共享（shared heap）+ 对象字面量 COW/缓存 |

ArkVM 的多 VM（worker）场景使「跨 VM 字符串共享」成为独特机会——单 VM 引擎无此问题。

## 4、本特性的设计/实现方案

### 4.1 子方向 A：字符串常量跨 VM 共享

1. **识别可共享字符串**：ConstantPool 的字符串条目（模块路径、属性名、字符串字面量），加载时标记为可跨 VM 共享；
2. **分配位置**：可共享字符串分配在 shared heap（sendable 字符串语义）；
3. **并发 intern**：复用 `EcmaStringTableMutex`（已有），首次跨 VM intern 加锁，后续 CAS/只读；
4. **hash 惰性计算的并发安全**：EcmaString 的 hash 字段按需计算并回写对象。shared 字符串被多 VM 引用后，hash 回写必须原子化（CAS 或构建期预计算），否则存在数据竞争——设计须明确该点并以 TSAN 验证（sendable 字符串已有先例，改造范围以目标 revision 现状为准）；
5. **生命周期**：worker VM teardown 时共享字符串不被回收（归 shared heap / Runtime 级），主 VM 或 Runtime 持有；
6. **GC**：shared heap 字符串由 shared GC 遍历；各 VM 字符串表内对 shared 对象的表项随 VM 销毁清理，不得触发对象释放。

量级：单 VM 的 ConstantPool 持有字符串（去重）15.38 MiB / 685,129 个（13 应用合计）。收益上界 = 15.38 MiB × (并发 VM 数 − 1) × worker 加载 abc 子集占比；无 worker 使用或 worker 不加载同 abc 的应用收益为 0。

### 4.2 子方向 B：Array/Object 字面量优化

1. **对象字面量 Properties/Elements COW 化**：对齐数组字面量已有的 `ENABLE_COW_ARRAY` 机制（`CloneArrayLiteral` 对 ≤10 元素数组在 NON_MOVABLE 空间共享 elements，`object_factory.cpp:539-560`），`CloneObjectLiteral`（`object_factory.cpp:517-537`）的深克隆路径改「backing COW 共享 + 写时复制」；
2. **模板对象克隆**：热路径重复字面量缓存模板对象，从模板克隆，减少属性填充成本；
3. **编译期辅助**：常量元素（数字/字符串/布尔）字面量生成预填充构建序列（可选）。

收益主体是创建路径的时间成本与 backing 峰值；空间收益取决于字面量对象在 js_object 83.69 MiB 中的占比（未归因，前置量化项）。

### 4.3 方案利弊

| 方案 | 优点 | 代价 |
|---|---|---|
| A：shared heap 字符串（选） | 消除跨 VM 线性重复（上界 15.38 MiB/VM） | 字符串表归属改造 + shared GC + hash 并发安全 |
| A'：仅共享只读字符串表 | 改动小 | 只覆盖只读字符串，收益受限 |
| B：COW 化（选） | 对齐数组字面量已有机制 | 写时复制正确性验证 |
| B'：模板克隆 | 减少创建时间成本 | 只省时间，空间收益未证实 |

## 5、DFX 分析

- 可诊断性：快照标注 shared 字符串与 COW backing 来源；
- 可运维性：worker teardown 的共享字符串清理日志。

## 6、可信分析

- **可靠性**：COW 写时复制屏障覆盖；共享字符串无悬垂（shared GC + 生命周期管理）；并发 intern 加锁；
- **安全性**：不涉及；**隐私/无害**：不涉及。

## 7、关键 DT 用例简述

| 测试用例名称 | 预置条件 | 用例关键步骤 | 预期结果 |
|--------------|----------|--------------|----------|
| 多 VM 字符串共享 | 主 VM + 2 worker 加载同一 abc | 对比字符串对象数 | 不随 VM 数线性增长 |
| 并发 intern | 多 VM 同时 resolve 同一字符串 | 首次 intern | 唯一对象，CAS 正确 |
| shared hash 并发计算 | 多 VM 同时首次求 hash | TSAN 构建 | 无数据竞争，hash 一致 |
| worker teardown | worker 退出 | 检查共享字符串 | 无泄漏/无悬垂 |
| 对象字面量 COW | 循环创建同构字面量 | 修改一个实例 | 其他实例不受影响（写时复制） |
