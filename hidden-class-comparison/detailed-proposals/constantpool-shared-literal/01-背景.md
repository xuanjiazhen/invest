# 对象字面量外置 Backing COW —— 背景

本方案只处理 ArkVM 对象字面量（Object Literal）的外置 `Properties` / `Elements` backing 写时复制（Copy-On-Write，COW）。目录名 `constantpool-shared-literal` 作为历史路径保留，不代表继续实施 ConstantPool 字符串跨 VM 共享。

## 1. 当前对象字面量创建路径

冻结源码基线：`ets_runtime@4ad6583a30981259b857579c61b5cc83b3530381`。

对象字面量模板由 ConstantPool 持有，执行字面量创建时从模板克隆新 `JSObject`。当前实现包含三条必须保持一致的路径：

| 路径 | 当前行为 | 源码位置 |
|---|---|---|
| Runtime 基础克隆 | 新建 `JSObject`，深拷贝 `Elements`、`Properties`，逐槽复制 inline properties | `object_factory.cpp:498-536` |
| Runtime 带 lexical env 克隆 | 深拷贝 backing；其中 `JSFunction` 还需克隆并重绑 `LexicalEnv` / `HomeObject` | `object_factory.cpp:603-673` |
| Compiler stub 克隆 | `CloneProperties` 分配新 backing，并对函数槽执行克隆和重绑 | `compiler/new_object_stub_builder.cpp:226-303,332-445` |

`CloneProperties` 的成本随 backing 长度和克隆次数重复发生。对象字面量如果创建后一直只读，这些私有 backing 的内容完全相同。

## 2. COW 可作用的对象范围

对象字面量实例包含三类存储：

1. **对象本体与 inline properties**：属于每个 `JSObject` 自身，不能 COW；现有逐槽复制保留。
2. **外置 `Properties` backing**：非空、非 dictionary、无需实例化重绑时可共享。
3. **外置 `Elements` backing**：非空、普通 fast elements、无需实例化重绑时可共享。

目标结构如下：

```text
ConstantPool object-literal template
  ├─ inline properties              每个实例继续独立复制
  ├─ Properties -> COWTaggedArray   模板与未写实例共享
  └─ Elements   -> COWTaggedArray   模板与未写实例共享

clone A --read----------------------> shared COW backing
clone B --first write--> mutable private copy --> write
```

对象仍然是独立实例；共享的只是初始外置 backing。任一实例首次写入前必须先复制对应 backing，之后写入私有副本。

## 3. 现有 COW 机制的可复用部分

ArkVM 已定义 `COW_TAGGED_ARRAY` / `COW_MUTANT_TAGGED_ARRAY`，`ObjectFactory::NewCOWTaggedArray` 在 NON_MOVABLE 空间分配 COW backing（`js_hclass.h:262-263,812-816`；`object_factory.cpp:3202-3225`）。数组字面量的 `CloneArrayLiteral` 已对小 backing 使用该类型（`object_factory.cpp:539-599`）。

本方案复用 COW backing 类型、GC 扫描和类型判定，但**不修改数组字面量**。数组现有实现仅作为对象字面量设计的代码参照，不能计入本方案收益。

普通 `JSObject` 写路径目前没有与 `JSArray::CheckAndCopyArray` 等价的统一写前脱离入口。属性写入、元素写入、扩容、删除、dictionary 转换、elements-kind migration，以及对应 compiler stub 都必须纳入改造审计；只修改 `CloneObjectLiteral` 会产生实例间可见数据污染。

## 4. 首版排除范围

- ConstantPool 字符串跨 VM 共享、字符串表归属、shared heap 字符串；
- 数组字面量 COW 及普通数组扩容后的 COW；
- 对象字面量 HClass 跨 VM 共享；
- 模板克隆、编译期预填充、字节码格式调整；
- inline properties COW；
- dictionary backing、超出阈值的 backing；
- 含 `JSFunction` / `AccessorData` 等需要按实例克隆或重绑的 backing。

上述排除项继续沿用现有深拷贝路径。

## 5. 现有数据能回答什么

- Top13 快照中的通用 `js_object` 总量为 83.69 MiB，但快照未保存对象字面量创建来源，不能将该总量归因给本方案。
- Kuaishou 配对快照中，ConstantPool 直接持有的 `JSObject` 前台为 8,291 个、后台 full-GC 为 8,160 个；现有 evidence 将 `JSObject` 与 `JSArray` backing 合并统计，不能单独得到对象字面量 COW 毛收益。
- 快照不记录克隆次数、首次写比例、写前 backing 长度和 COW 脱离历史，因此不能从存量直接推导净收益。

正式立项数据必须来自 `CloneObjectLiteral` 与首次写脱离插桩，并用 clean A/B 快照分别验证 shallow、Region used/committed 和 RSS/PSS。插桩设计见 `05-插桩patch.md`。
