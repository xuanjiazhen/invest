# LayoutInfo 确定性容量策略：需求

## 1. 目标

在保持属性访问、枚举、transition、AOT/PGO、serializer 和 GC 语义不变的前提下，减少 LayoutInfo 创建时不必要的尾部 capacity，且不因过度压缩导致后续追加频繁扩容。

## 2. 策略目标函数

对一个布局族选择初始 capacity `C`，总成本应同时考虑初始 slack 和后续扩容：

```text
cost(C)
 = initial_slack_cost(C)
 + expected_growth_copy_cost(C)
 + decision/profile_cost(C)
 + fallback_risk_cost(C)
```

不得把 `C = effective_property_count` 作为无条件最优解。它只在最终布局已经确定时成立。

## 3. 适用范围

### 3.1 首版可实施

- 创建者掌握最终 property count，且源码证明创建后不再沿同一 LayoutInfo 追加；
- 固定 builtin/global shape，属性清单和后续变更边界明确；
- 版本化外部布局信息与当前 runtime、ABI、bundle、class identity 和属性 schema 完全匹配，并且具备容量不足回退路径。

### 3.2 首版排除

- 普通动态 transition；
- PGO root/child family 的 `maxNumOfProps`，直到 family 和 HClass inline capacity 完成联合验证；
- 仅凭 heap snapshot 观察到空洞的对象；
- N-API class 中没有独立 finality 契约的路径；
- SharedHeap、Sendable、dictionary、AOT 兼容边界未关闭的路径；
- 只有低概率变化证据、没有 fallback 的无保护精确分配。

## 4. 外部信息和策略选择

可使用的信息包括：

- 编译器/AOT/PGO 给出的最终属性数或 family 最大属性数；
- 固定 builtin 的源码属性清单；
- 系统模块或应用的版本化 class schema；
- 运行时画像中的最终属性数分布、扩容率、copy bytes 和创建延迟。

所有外部信息必须携带：

```text
runtime/source revision
ABI/configuration
bundle/module identity
class/constructor identity
property schema/order
profile generation version
```

任一不匹配即不使用，继续当前 GROW。

## 5. 验收

1. feature-off 与现状行为一致；
2. capacity 不足时通过现有 copy/extend 路径处理，不越界；
3. 属性、descriptor、representation、TrackType、PGO/AOT、serializer 和 GC 回归通过；
4. 统计 initial capacity、最终属性数、扩容次数、copy bytes、profile hit/miss/invalidation 和延迟；
5. clean A/B 分别报告 LayoutInfo shallow、GC、Region used/committed、RSS/PSS 和峰值；
6. 只有在物理收益为正且创建 P95 不恶化时才扩大范围。
