# LayoutInfo 确定性容量策略：方案设计

## 1. 设计结论

本方案不把所有 LayoutInfo 统一改为紧凑分配，而是采用**分层容量策略**：

```text
创建前能证明最终布局
    -> 精确 capacity
创建前不能证明，但有可靠外部布局信息
    -> 预测 capacity + 受控余量
创建前没有可靠信息
    -> 现有 GROW
```

策略只改变新建 LayoutInfo 的 capacity，不改变 LayoutInfo 的物理格式、读取路径、HClass 布局或普通 transition 语义。

## 2. 为什么不能无条件使用精确属性数

精确分配会把原来一次完成的属性追加变成后续 copy/extend。当前普通新增属性路径在 capacity 足够时直接 `AddKey`，容量不足时执行 `ExtendLayoutInfo`；如果属性数量不匹配，还可能执行 `CopyAndReSort`（`arkcompiler_ets_runtime/ecmascript/js_hclass-inl.h:428-453`；`object_factory.cpp:3469-3533`）。

因此，精确分配的额外代价包括：

- 额外 LayoutInfo 分配；
- 旧物理槽复制；
- 新数组初始化和 GC 记录；
- 更高的创建延迟和临时峰值；
- 可能破坏已有 PGO/AOT 或 transition family 的容量假设。

本方案不追求“零 slack”，而是最小化总成本：

```text
总成本
= 初始预留槽成本
+ 未来扩容/复制成本
+ 预测判断成本
+ 错误预测带来的性能成本
```

## 3. 容量策略

### 3.1 Strategy 0：现有 GROW

适用：

- 没有可靠的属性数量信息；
- 普通 JavaScript 动态对象；
- 后续可能沿同一 LayoutInfo 追加；
- PGO/AOT family capacity 尚未完成证明；
- 外部信息版本不匹配或置信度不足。

行为保持现状：

```text
capacity = min(N + 4, MAX_FAST_PROPS_CAPACITY)
```

这是默认 fallback，不能删除。

### 3.2 Strategy 1：静态精确 KEEP

适用：创建函数已经掌握本次最终 property count，且同一 LayoutInfo 在返回后不会再追加。

```text
capacity = final_property_count
```

必须同时满足：

1. 属性列表或最终数量由当前创建事务完整决定；
2. 创建过程中的所有写入都在该范围内；
3. 返回后不沿该 LayoutInfo 追加；
4. 后续变更会产生新 HClass/LayoutInfo 或走既有 copy/extend；
5. HClass inline capacity、offset、object size 不依赖被删除的 slack。

已显式使用 KEEP 的路径直接作为基线，不重复计算收益：class extractor、部分 PGO restore、默认 class HClass 和 empty LayoutInfo。

### 3.3 Strategy 2：外部信息预测 + 受控余量

当创建前无法证明绝对最终，但可以从外部信息得到稳定的属性上界时，使用：

```text
capacity = min(predicted_final_count + reserve, MAX_FAST_PROPS_CAPACITY)
```

其中：

- `predicted_final_count`：由 PGO/AOT/class metadata/历史运行画像提供；
- `reserve`：小的整数余量，不固定写死，由离线算法选择；
- 预测信息必须与当前代码版本、ABI、类/构造函数 identity 和属性顺序匹配；
- 预测失效时回退到 GROW 或更保守容量，不能继续使用过期预测。

该策略不是无条件压缩。它保留少量余量，目标是在“每次都精确扩容”和“固定 +4 或更大预留”之间取得平衡。

### 3.4 Strategy 3：运行时学习后用于后续创建

对同一可识别布局族，第一次或前若干次创建继续使用 GROW，并记录：

```text
observed_final_property_count
max_property_count
append_after_initialization
extend_count
copy_bytes
```

后续同族创建只有在满足稳定性条件时才采用预测容量，例如：

```text
prediction = max_count_seen + reserve
```

建议的状态机：

```text
UNKNOWN
  -> WARMING（收集样本，仍使用 GROW）
  -> STABLE（达到样本数和稳定条件，可使用预测容量）
  -> INVALIDATED（版本/构造器/原型/属性顺序变化，回到 WARMING）
```

该状态机必须绑定明确的布局 identity，不能仅按属性名或类名匹配。对于可能跨 VM、跨 bundle 或跨版本变化的外部 key，应拒绝命中。

### 3.5 三大已识别 KEEP 转换路径（逐路径浪费分析与 V8 对照）

#### 3.5.1 路径 G1：函数 HClass LayoutInfo（最大浪费源）

**源码位置**：`object_factory.cpp:2031-2056`。

**浪费产生过程**：每个函数声明/表达式在 VM 中创建 HClass 时，`CreateLayoutInfo(2, GROW)` 分配 capacity=2+4=6（self_size=112 B），但函数的属性集是封闭的（仅 `length` 和 `name`），填入 2 个属性后 4 个 slack 槽（64 B）永久闲置。函数属性在创建时一次性全部填入，此后不会再有属性追加到该 LayoutInfo。

改为 `GrowMode::KEEP` 后 capacity=2（self_size=48 B），两次 `AddKey` 均原地写入，行为完全不变。**性能劣化为零，不存在累加**——属性集封闭，无后续追加场景。

V8 对照：V8 不为每个函数独立创建 DescriptorArray。同一种 FunctionKind 的所有函数共享 native context 缓存的同一个 Map（含同一个 DescriptorArray），per-context 仅一份。ArkVM 每个函数 HClass 独立创建 LayoutInfo，是两者的结构性差异。

#### 3.5.2 路径 G10：字典→fast 迁移

**源码位置**：`js_hclass.cpp:725-750`。

**浪费产生过程**：对象从字典模式迁移回 fast 模式时，`CreateLayoutInfo(numberOfProperties, GROW)` 分配 capacity=N+4，但迁移时已知准确的属性数 N，逐个 `AddKey` 后 4 个 slack 槽闲置。

改为 `GrowMode::KEEP` 后 capacity=N，N 次 `AddKey` 均原地写入。唯一风险是迁移后如果对象又被追加新属性，将触发一次 `ExtendLayoutInfo`（分配新数组 + 拷贝 ≈ 110 ns）。**劣化为一次性 ~110 ns，不累加**——Extend 后新数组获得 +4 slack（与 GROW 初始分配相同），后续行为完全收敛。迁移本身意味着 VM 判定该对象形状已稳定，迁移后再追加的概率极低。

V8 对照：V8 的 `JSObject::MigrateSlowToFast`（objects.cc）在迁移时调用 `DescriptorArray::Allocate(isolate, numberOfProperties, 0)`——**slack 显式传 0**，精确分配，与 KEEP 等效。V8 已在此路径采用精确容量。

#### 3.5.3 路径 G11：对象字面量属性填充

**源码位置**：`object_factory.cpp:5720-5740`。

**浪费产生过程**：对象字面量 `{x:1, y:2, z:3}` 的属性数在编译期已知（propertyCount=3），`CreateLayoutInfo(3, GROW)` 分配 capacity=7，填入 3 个属性后 4 个 slack 槽闲置。

改为 `GrowMode::KEEP` 后 capacity=3，3 次 `AddKey` 原地写入。唯一风险是字面量创建后动态追加属性（`obj.w = 4`），将触发一次 ExtendLayoutInfo（~110 ns）。**劣化为一次性 ~110 ns，不累加**——Extend 后 capacity=3+4=7，与 GROW 初始分配完全相同，后续零差异。严格 ArkTS 中未声明属性不可赋值，动态追加在编译期即被禁止。

V8 对照：V8 的对象字面量通过 `ObjectLiteralMapFromCache`（factory.cc）从 native context 缓存获取初始 Map，属性数精确匹配（`kMapCacheSize=128`，按属性数索引）。后续属性追加走 transition 链（`ShareDescriptor` + `SlackForArraySize`），使用条件性 slack 而非固定 +4。

#### 3.5.4 三路径汇总

| 路径 | 浪费量级 | 改 KEEP 后劣化 | 累加 | 风险 | V8 行为 |
|------|---------|---------------|------|------|---------|
| G1 函数 HClass | 64 B × ~20,000 ≈ **1.2 MiB** | **零** | 不会 | **零** | per-context 共享，不独立创建 |
| G10 字典迁移 | 64 B × ~7,000 ≈ **0.4 MiB** | 一次性 ~110 ns | 不会 | 极低 | **slack=0，已精确** |
| G11 对象字面量 | 64 B × ~10,000 ≈ **0.6 MiB** | 一次性 ~110 ns | 不会 | 低（严格 ArkTS 为零） | 缓存精确初始 Map |
| **合计** | **~2.2 MiB** | | | | |

三条路径的改动均为 1-2 行参数变更（`GROW` → `KEEP`），不需要修改任何逻辑代码。G1 为零风险纯收益；G10/G11 的劣化均为一次性且不累加（Extend 后的 capacity 与 GROW 初始分配一致，从此走同一条路径）。

## 4. 外部信息来源和使用方式

| 来源 | 可提供信息 | 使用边界 |
|---|---|---|
| PGO/AOT class layout metadata | root 属性数、child 最大属性数、属性顺序 | 必须与当前 PGO/AOT 版本、HClass capacity 和 transition family 一致；当前 PGO family 先不改 |
| 编译器/字节码 class metadata | 静态 class literal 的属性列表或上界 | 只适用于 metadata 完整且运行时不会再注入属性的路径 |
| N-API 注册描述符 | 当前 static/non-static 数量和顺序 | 只能覆盖注册事务；不能单独证明返回后不再修改 class |
| 历史运行画像 | 某布局族的最终属性数分布、扩容概率 | 只能用于预测余量；不能作为无保护的安全证明 |
| 版本化应用/系统模块白名单 | 已知固定 class schema、版本和 bundle | 需要版本失效、bundle identity、VM/线程域和 fallback |
| 运行时自学习计数 | 实际追加、扩容和复制情况 | 适合后续实例策略选择；需限制表大小和生命周期 |

外部信息只决定 capacity，不改变 LayoutInfo key/Attr 内容和 HClass 解释规则。

## 5. 离线余量选择算法

对每个布局族，离线输入最近多个同版本、同 ABI、同配置、同场景的运行样本，记录最终属性数量 `N`。不要直接取均值；容量不足的代价通常高于多一个 slack 槽，因此使用带惩罚的决策：

```text
candidate_capacity c ∈ [base_count, max_allowed]

cost(c)
  = λ_slack × E[max(c - N, 0)]
  + λ_growth × E[growth_cost(N, c)]
  + λ_tail × P(N > c)
```

其中：

- `base_count` 是当前创建事务已知的属性数；
- `growth_cost` 至少包含一次 `ExtendLayoutInfo` 的分配、复制、初始化和写屏障成本；
- `λ_slack`、`λ_growth`、`λ_tail` 是由同设备基准测试标定的工程权重，不在没有测量时伪造固定数值；
- `P(N > c)` 是超出预测容量的概率；
- 最终选择使实测或标定成本最小的 `c`，而不是默认选择最小 `c`。

在没有性能标定时，只输出候选曲线，不自动启用：

```text
c = base_count + 0 / 1 / 2 / 4
```

分别测量 slack 字节、扩容率、复制字节、创建 P50/P95 和峰值，再选择策略。

### 5.1 保守分位数策略

如果只能获得历史最终属性数样本，可以选择高分位数：

```text
predicted_capacity = percentile(N_samples, q) + reserve
```

但 `q` 必须通过独立验证集和性能代价选择，不能事后挑选最优结果。版本或运行环境变化后重新训练/验证。

### 5.2 分层策略

推荐按风险分层：

```text
高确定性：capacity = exact N
中确定性：capacity = P99(N) + 1
低确定性：capacity = GROW(N)
```

其中“P99 + 1”只是候选算法形式，不是未经标定的固定发布参数。只要发生超出预测的追加，就记录并触发该布局族降级。

## 6. 运行时策略选择伪代码

```text
SelectLayoutInfoCapacity(context):
    if context.is_read_only_constant:
        return KEEP(context.final_property_count)

    if context.creation_site in static_final_whitelist
       and context.finality_proven:
        return KEEP(context.final_property_count)

    if context.external_profile.matches(
           source_revision, abi, bundle_id, class_id, schema_version)
       and context.profile.is_valid
       and context.profile.confidence >= configured_threshold:
        c = min(context.profile.predicted_count + context.profile.reserve,
                MAX_FAST_PROPS_CAPACITY)
        return GROW_TO(c)  // 受控余量；不是无条件 exact N

    if context.runtime_family_state == STABLE
       and context.family_profile.valid_for_current_vm:
        return GROW_TO(context.family_profile.predicted_count + reserve)

    return GROW
```

`GROW_TO(c)` 是方案级语义：允许初始 capacity 为 `c`，但仍保留现有扩容路径。它不能改变 `NumberOfElements()`，也不能使 LayoutInfo 写入超过物理 capacity。

## 7. 失效和降级条件

外部预测或运行时画像遇到以下情况立即失效：

- 代码/ABI/runtime revision 变化；
- bundle、模块、类 identity 变化；
- 原型链或继承关系变化；
- 属性顺序、descriptor、representation 或 static/non-static 分类变化；
- PGO/AOT profile 与当前加载产物不匹配；
- 发生一次未预期的属性追加或扩容；
- SharedHeap/LocalHeap/VM 域不匹配；
- 计数器发现扩容率、复制字节或 P95 创建耗时超过门限。

失效后：

```text
停止使用预测容量
清除或隔离旧 profile
回到 GROW
保留事件计数
```

## 8. 竞品对应做法

V8 有公开的 in-object slack tracking：初始 map 会依据编译/构造信息预留额外 in-object property 空间；通过 construction counter 在若干次构造后观察整个 map transition tree 的实际最大属性使用量，再收缩 map 的 instance size。V8 官方说明同时强调：初始预留是为了允许构造函数后继续添加少量属性，slack tracking 在后续阶段回收未使用空间；transition tree 的后代最大使用量会影响最终保留空间（V8 官方：[Slack tracking in V8](https://v8.dev/blog/slack-tracking)）。

ArkVM 当前也已有相近的“先保守、后收敛”机制，但作用对象主要是 HClass 描述对象实例的 in-object property size：

- `--enable-inline-property-optimization` 同时启用 slack tracking（`ecmascript/js_runtime_options.cpp:231`）；
- `JSFunction::CalcuExpotedOfProperties` 根据方法信息计算预期属性数并启动 tracking（`ecmascript/js_function.cpp:214-227,242-266`）；
- `JSHClass` 使用 construction counter，构造若干对象后遍历 transition tree，计算最大属性数并更新 object size（`ecmascript/js_hclass.h:2180-2192`；`js_hclass-inl.h:353-381`；`js_hclass.cpp:932-985`）；
- 新对象分配和 compiler stub 在 tracking 期间使用特殊 filler，并在计数结束时触发收敛（`object_factory.cpp:1895-1917`；`compiler/new_object_stub_builder.cpp:472-525`）。

这说明竞品和 ArkVM 的共同思路不是“一开始永远精确分配”，而是：

```text
先用外部/编译信息给出预测
保留有限余量保证扩展性能
通过构造样本和 transition family 观察实际使用
在安全边界内收缩后续分配
```

但上述 ArkVM slack tracking 主要针对对象实例的 inline property size，不能直接证明 LayoutInfo capacity 可以复用同一状态机。LayoutInfo 仍需单独记录其自身的追加、扩容和 copy 行为。

## 9. 建议的实施顺序

1. **只读插桩**：按 creation site 和 layout kind 记录初始 capacity、最终 property count、追加、扩容、复制字节和时延；
2. **静态低风险点**：只把已证明 final-by-construction 的 GROW 调用点改为显式 KEEP；
3. **外部 profile 实验**：对同版本、同 bundle、同 class schema 试验 `predicted + reserve`，默认可回退；
4. **运行时学习**：验证 WARMING/STABLE/INVALIDATED 状态机，限制表规模和失效条件；
5. **PGO family**：单独关闭 HClass inline capacity、root/child transition、AOT restore 后再评估；
6. **发布**：必须通过 clean A/B，确认扩容率、复制字节和创建 P95 不恶化，并分别测量 shallow、Region、RSS/PSS。

## 10. 验收指标

```text
initial_capacity
final_property_count
slack_capacity_slots
slack_bytes
append_after_create
extend_count
copy_bytes
profile_hit/miss/invalidation
create_latency_p50/p95
LayoutInfo shallow
Region used/committed
peak RSS/PSS
```

### 必须满足

- 未命中或失效 profile 时行为等价于现有 GROW；
- compact/预测容量不足时不越界，走现有 copy/extend；
- property lookup、enumeration、descriptor、representation、TrackType、PGO/AOT、serializer 和 GC 结果不变；
- 预测收益按实际物理 `self_size`、扩容成本和 clean A/B 计算；
- 不把 snapshot slack 上界直接写成发布收益。
