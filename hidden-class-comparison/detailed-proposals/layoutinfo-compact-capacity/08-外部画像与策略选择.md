# LayoutInfo 确定性容量策略：外部画像与策略选择

## 1. 画像输入

外部信息只用于选择初始 capacity，不改变 LayoutInfo 的 key/Attr 语义。候选画像必须绑定：

```text
runtime/source revision
ABI and build configuration
bundle/module identity
class/constructor identity
property schema and order
profile schema version
```

推荐输入：

- 固定 builtin 的源码属性清单；
- 编译器/AOT/PGO 的 class layout metadata；
- 同版本、同 ABI、同 bundle 的历史运行数据；
- 首轮 GROW 运行产生的 `final_property_count`、追加次数、扩容次数、copy bytes 和创建延迟。

画像不匹配、过期或缺少属性顺序时，直接回退 GROW。

## 2. 容量决策

对同一个布局 identity，先确定创建事务已知的属性数 `base_count`，再从候选集合选择初始 capacity：

```text
C0 = base_count
C1 = percentile(final_property_count, q) + reserve
C2 = current GROW result
```

选择目标不是最小 capacity，而是最小化：

```text
cost(C)
 = λ_slack × E[max(C - N, 0)]
 + λ_extend × E[extend_count(C)]
 + λ_copy × E[copy_bytes(C)]
 + λ_latency × create_p95(C)
```

`λ` 由同设备基准实验标定。没有标定数据时只生成曲线，不自动改变运行时策略。

推荐的初始实验档位：

```text
exact: base_count
low-risk: base_count + 1
balanced: validated percentile + reserve
fallback: existing GROW
```

`percentile`、`reserve` 和切换阈值必须在训练样本之外的验证样本上确定。

## 3. 运行时状态机

```text
UNKNOWN
  -> WARMING: 无有效画像，使用 GROW
  -> STABLE: 画像匹配且验证通过，使用 C
  -> INVALIDATED: 行为/版本/schema 变化，回到 GROW
```

进入 `STABLE` 至少需要：

1. 多次同 identity 样本；
2. 追加/扩容/copy 行为满足预设门限；
3. 属性顺序、descriptor、representation 和原型/继承关系一致；
4. profile 与当前 runtime/ABI/bundle 完整匹配；
5. 已验证容量不足 fallback。

一旦发生未预期追加、扩容、schema 变化或性能回退，立即进入 `INVALIDATED`。

## 4. 适用范围

### 4.1 可直接使用 exact capacity

- 源码固定属性清单的 builtin/global shape；
- 创建函数一次性接收完整最终 property list，且后续不会沿同一 LayoutInfo 追加；
- 已有显式 KEEP 的路径作为基线。

### 4.2 只能使用预测 capacity

- 运行时属性数通常稳定，但存在低概率追加；
- 外部 profile 可提供同版本同 identity 的历史分布；
- 具备明确的 extend/copy fallback。

### 4.3 必须使用 GROW

- 普通动态 transition；
- PGO root/child family 尚未联合证明；
- N-API class 没有 finality 契约；
- 外部画像不匹配或行为不稳定；
- SharedHeap/Sendable/dictionary/AOT 语义未关闭。

## 5. 与现有机制的关系

V8 公开采用 in-object slack tracking：初始分配使用编译/构造信息提供的预测并保留余量，通过 construction counter 观察 map transition tree 的实际属性使用情况，之后按整个 family 的实际最大使用量收缩后续对象的 instance size（V8 官方文档：`https://v8.dev/blog/slack-tracking`）。

ArkVM 也有相近的 HClass/object-size tracking：`--enable-inline-property-optimization` 可启用 slack tracking；`JSFunction::CalcuExpotedOfProperties` 计算预期属性数，`JSHClass` construction counter 在构造样本后遍历 transition tree 更新 object size（`arkcompiler_ets_runtime/ecmascript/js_runtime_options.cpp:231`；`js_function.cpp:214-227,242-266`；`js_hclass.h:2180-2192`；`js_hclass-inl.h:353-381`；`js_hclass.cpp:932-985`）。

这两个机制提供的是策略参考：先预测、有限预留、观察、再收敛。它们不能直接证明 LayoutInfo 可以复用同一状态机，因为 LayoutInfo backing capacity 与对象实例 inline capacity 的生命周期和写入者不同。LayoutInfo 需要独立记录创建、追加和扩容事件。

## 6. 最小验证实验

对每个候选布局族使用同一 workload 比较：

```text
existing GROW
exact base_count
base_count + 1
validated percentile + reserve
```

必须记录：

- 初始 capacity 和最终属性数；
- slack bytes；
- extend/copy 次数和 copy bytes；
- 创建 P50/P95；
- 属性访问、枚举、GC 结果；
- LayoutInfo shallow；
- Region used/committed；
- 峰值 RSS/PSS。

策略只有在验证集上同时满足语义一致、无越界、创建延迟不恶化且物理收益为正时才可发布。
