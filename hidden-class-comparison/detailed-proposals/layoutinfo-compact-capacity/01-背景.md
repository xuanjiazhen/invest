# LayoutInfo 确定性容量策略：背景

## 1. 目标对象

`LayoutInfo` 是 `JSHClass` 的属性描述数组，私有继承 `TaggedArray`。每个属性占一个 key 槽和一个 Attr 槽，`GetLength()` 表示物理槽数，`ExtraLength` 表示当前有效属性数（`arkcompiler_ets_runtime/ecmascript/layout_info.h:25-35`；`layout_info-inl.h:25-48`）。

因此：

```text
physical TaggedArray slots = 2 × capacity
self_size = 16 + 16 × capacity bytes
```

创建时整个 capacity 都会初始化，尾部预留槽是真实的 LayoutInfo shallow 内存（`layout_info.cpp:21-28`；`tagged_array.h:80-85`）。

## 2. 当前分配策略

`ObjectFactory::CreateLayoutInfo` 默认参数为 `GrowMode::GROW`（`object_factory.h:467-468`）。GROW 调用：

```text
capacity = min(properties + MIN_PROPERTIES_LENGTH, MAX_FAST_PROPS_CAPACITY)
```

`MIN_PROPERTIES_LENGTH` 当前为 4（`object_factory.cpp:3459-3465`；`layout_info.h:92-96`；`js_hclass.h:411`）。当调用者传入最终属性数 `N` 且未触及上限时，默认 GROW 比紧凑 `capacity=N` 多分配 4 个 property capacity，即 64 B。

但现有调用点并不统一：class extractor、部分 PGO restore、默认 class HClass 和 empty LayoutInfo 已明确使用 `GrowMode::KEEP`（`class_info_extractor.cpp:206-235,248-290`；`js_hclass.cpp:1483-1529`；`object_factory.cpp:2082-2105`；`global_env_constants.cpp:575-579`）。因此不能把全部 LayoutInfo 或全部 PGO 路径都按 `N+4` 计算。

## 3. 问题边界

快照可以显示 physical capacity 大于有效属性数，但只反映采集时的终态，不反映 LayoutInfo 的创建来源、后续追加历史或某个 PGO family 的最大属性数。当前普通 transition 在 capacity 足够时会直接 `AddKey`，不足时才复制/扩容（`js_hclass-inl.h:428-453`）；PGO root/child 还会按 family 计算 `maxNumOfProps` 并继续构造 child（`pgo_hclass_generator.cpp:61-65,117-150`；`js_hclass.cpp:1551-1590`）。

所以本方案只接受两类证据：

1. **静态最终性**：创建点已经掌握最终属性数，且源码证明创建完成后不会沿同一 LayoutInfo 使用预留容量；
2. **运行时闭环**：插桩证明候选类别的追加/扩容为零，且 compact 后仍有明确的越界保护和现有 copy/extend fallback。

“改变概率很小”只能用于收益预测，不能单独作为发布条件。未知路径继续使用 GROW；已明确最终的路径才使用 KEEP。
