## 6. 复核意见与源码优先验证清单（2026-09-03）

### 6.1 复核范围与结论

本节是在不修改 ArkTS VM 源码的前提下，对本文三条 GROW→KEEP 候选路径、KEEP 总览、快照收益和 V8 对照的复核结果。源码基线为：

```text
arkcompiler_ets_runtime
branch: master
revision: 3fa79cf3ff01c1cb34683690d2c69710eac5f323
```

总体结论：本文可以作为候选路径分析材料，但当前不能把“三条路径均已证明可安全改为 KEEP”“方案 A 为零风险纯收益”或“G1/G10/G11 的收益已由快照归因”作为实施结论。建议先完成源码侧的写入闭包和对象群体归因，再进行运行时插桩与 A/B 验证。

当前建议分类如下：

| 路径 | 复核后的暂定分类 | 复核结论 |
|---|---|---|
| G1 `CreateFunctionClass` | `source candidate` | 创建的是 HClass，不是每个 JSFunction 实例的 LayoutInfo；实际写入属性依赖 `FunctionKind`，收益不能按函数实例数乘算 |
| G10 字典→fast | `BUILD_EXACT_WITH_FALLBACK` 候选 | 迁移事务内 `EntriesCount()` 可给出初始最大写入量；后续 transition 仍需保留并验证 `ExtendLayoutInfo`/`CopyAndReSort` fallback |
| G11 大对象属性构造 | `source candidate` | 当前调用点是 N-API/工厂大对象构造路径，不能直接等同于普通语言对象字面量；小对象字面量另有 root HClass cache 和 transition 路径 |

### 6.2 已发现的问题

#### P0：G1 的对象数量和属性集合归因不成立

1. `ObjectFactory::CreateFunctionClass` 创建的是一个函数类 HClass 及其 LayoutInfo，不是每个 JSFunction 实例各自创建 LayoutInfo。内建函数实例通常通过 `GetHClassByFunctionKind` 取得环境中已有的 HClass；相关路径见 `ecmascript/object_factory.cpp:1929-1941`、`1944-1953` 和 `1990-1995`。
2. `CreateFunctionClass` 的 LayoutInfo 创建参数并不总是固定为 2：`inlinedProps == DEFAULT_CAPACITY_OF_IN_OBJECTS` 时使用 `JSFunction::LENGTH_OF_INLINE_PROPERTIES`，否则使用 `inlinedProps`，见 `ecmascript/object_factory.cpp:2030-2037`。
3. 实际 `AddKey` 集合依赖 `FunctionKind`：必写 `length`；非 class constructor 才写 `name`；满足 `HasPrototype(kind)` 的路径还会写 `prototype`，见 `ecmascript/object_factory.cpp:2039-2075`。因此“固定 length+name”“每个 LayoutInfo 只有 2 个属性”的推导不适用于所有 G1 调用。
4. 该 HClass 还显式设置为可扩展，见 `ecmascript/object_factory.cpp:2022-2028`。这不能单独证明同一 LayoutInfo backing 一定会追加，但足以否定“生命周期天然封闭、风险为零”的表述。
5. `builtins.cpp` 中的调用点主要用于环境初始化和不同函数类型的 HClass 建立，见 `ecmascript/builtins/builtins.cpp:236-289`、`394-407`、`748-751`。在没有 `CreateFunctionClass` 调用次数、`FunctionKind`、`inlinedProps` 和后续 transition 计数前，不能使用“64 B × 函数数量”或本文的约 `1.2 MiB` 作为 G1 收益。

因此，G1 应从“已证明的每函数固定收益”降级为源码候选。需要先证明目标 HClass 的创建次数、实际属性闭包、后续 transition 关系和 LayoutInfo backing 生命周期。

#### P0：G10 的初始精确容量可行，但文档混淆了迁移阶段和后续 transition 阶段

`OptimizeAsFastProperties` 从 dictionary 的 `EntriesCount()` 得到属性数量，并在迁移阶段创建 LayoutInfo、按 `0..numberOfProperties-1` 写入属性，见 `ecmascript/js_hclass.cpp:719-746`。因此，初始迁移事务使用 `GrowMode::KEEP` 具有源码候选依据。

但该 HClass 后续的动态属性路径仍需按普通 transition 处理。`AddPropertyToNewHClass` 在顺序不匹配时进入 `CopyAndReSort`，容量不足时进入 `ExtendLayoutInfo`，之后才调用 `AddKey`，见 `ecmascript/js_hclass-inl.h:428-452`。因此 G10 不能被描述为“迁移后追加必然在原 LayoutInfo 上 Extend”；必须确认 child HClass、LayoutInfo backing 和复制路径的实际关系。

此外，字典→fast 不只分配 LayoutInfo。对象属性值迁移还会单独创建 out-properties backing，见 `ecmascript/js_object.cpp:477-511`。G10 的性能模型必须同时记录 dictionary 遍历、HClass 更新、LayoutInfo 创建、out-properties 创建和值迁移，不能只用一次 LayoutInfo 扩容的估算代替整个迁移事务。

本文 `{x,y,z}` 追加到 `t` 的示例还存在容量边界问题：当初始 `N=3`、`GROW capacity=7` 时，第 7 个属性写入后是“达到容量”，下一次追加才需要扩容，不能把写入第 7 个属性本身描述为已经触发 Extend。扩容次数和复制槽数必须按每次追加前的 `NumberOfElements()`、目标 offset 和实际分支重新计算。

#### P0：G11 的路径命名和对象群体归因不准确

`object_factory.cpp:5722` 和 `5829` 位于：

```text
CreateLargeJSObjectWithProperties
CreateLargeJSObjectWithNamedProperties
```

它们接收运行时传入的 `propertyCount`、keys 和 descriptor/value 参数，属于 N-API/工厂的大对象属性构造路径，见 `ecmascript/object_factory.cpp:5710-5747`、`5818-5849`。这两个调用点不能直接等同于普通 ArkTS/JavaScript 源码中的：

```ts
const point = { x: 1, y: 2, z: 3 };
```

普通小对象字面量路径先经过 `CreateJSObjectWithProperties`、`GetObjectLiteralRootHClass` 和 `SetPropertyOfObjHClass`，见 `ecmascript/object_factory.cpp:5671-5707`、`4367-4388`、`4409-4439`。该路径还涉及 object-literal root HClass cache、`literalLength`、`maxPropsNum` 和 transition chain，不能简化为一次 `CreateLayoutInfo(propertyCount, GROW)`。

因此 G11 必须至少拆成：

1. N-API/工厂大对象属性构造；
2. 普通小对象字面量 root/cache/transition；
3. PGO/AOT 对象字面量恢复。

另外，`propertyCount` 是本次运行时 API 调用得到的完整输入，不应表述为普通语言对象字面量的“编译期已知”。“ArkTS 编译期禁止对象后续追加”也只能约束特定语言、编译配置和调用路径，不能作为所有共享 HClass 的运行时生命周期证明。

#### P1：KEEP 总览中的若干“零浪费”结论未经过生命周期验证

1. 总览写的是“KEEP 精确分配 11 个路径”，但表格只列出了 K1-K7 七项，存在直接的数量不一致。
2. `js_hclass.cpp:1495` 的 PGO root 使用 `maxNum` 创建 KEEP LayoutInfo，但 HClass 的当前属性数使用 `numOfProps`，见 `ecmascript/js_hclass.cpp:1483-1512`。`maxNum-numOfProps` 可能是 transition family 语义，不能直接标记为零浪费或可裁剪空间。
3. `js_hclass.cpp:1526` 的 cached object-literal root 先按 `literalLength` 建立 LayoutInfo，随后通过 `SetPropertyOfObjHClass` 建立 child transition，见 `ecmascript/js_hclass.cpp:1515-1548`。该 LayoutInfo 属于 root/family 构建过程，不能仅因使用 KEEP 就推导为“当前已用数等于最终容量”。
4. `object_factory.cpp:2085` 的默认 class prototype 路径创建 `size` 容量，但当前代码只显式调用一次 `AddKey`，随后把 HClass 的 `NumberOfProps` 设为 `size`，见 `ecmascript/object_factory.cpp:2082-2099`。必须分别核对 `NON_STATIC_RESERVED_LENGTH`、`CONSTRUCTOR_INDEX`、LayoutInfo 的 `NumberOfElements()` 和 HClass 的 `NumberOfProps()`，不能仅按 HClass 属性数标记为零浪费。
5. `LayoutInfo` 的“4 个预留槽位”应统一写成“4 个 property-capacity units，等价于 8 个底层 TaggedArray tagged slots、约 64 B”。源码中的 `LayoutInfo` 以 key/Attr 两个 tagged slot 表示一个属性，见 `ecmascript/layout_info.h:30-35`、`87-95` 和 `ecmascript/layout_info-inl.h:25-32`。

#### P1：快照能够证明全量结构性 slack，不能证明 G1/G10/G11 的收益

当前快照 census 的可验证范围是 LayoutInfo 物理 `self_size`、effective property count 和结构性差额，不包含 creation-site、FunctionKind、字典迁移来源、object-literal 来源、PGO family 或后续 Extend 历史。

当前已复核的数字为：

| 样本 | admitted LayoutInfo | positive slack | 当前 shallow | 结构性 slack 上界 |
|---|---:|---:|---:|---:|
| 快手前台 | 69,735 | 47,050 | 13,574,224 B | 3,348,784 B（约 3.19 MiB） |
| 快手后台 | 62,482 | 41,580 | 11,963,344 B | 3,106,544 B（约 2.96 MiB） |
| TOP13 合计 | 735,734 | 389,368 | 114,555,552 B | 20,662,928 B（约 19.71 MiB） |

这些数字的正确标签是“raw snapshot + structural upper bound”。它们不能推出：

```text
G1/G10/G11 各自的 LayoutInfo 数量
G1/G10/G11 各自的 64 B 收益
G1/G10/G11 各自的后续追加概率
可实现的 RSS/PSS、Region committed 或进程峰值收益
```

特别是 `positive slack` 可能同时包含普通 GROW 余量、transition/family reserve、已经扩容过的 LayoutInfo 和仍可能追加的布局。没有 creation-site 归因前，本文的 G1 约 30%、G10 约 10%、G11 约 15% 以及方案 A 约 2.2 MiB 均不可由当前快照重现。

#### P1：性能数字和方案 B 结论目前不是实测结论

本文中的 `~10 ns`、`~100 ns`、`~110 ns`、`~0.28 ms`、`~0.8-1.5 MiB`、`96% 属性 ≤9` 等数字，目前没有对应的 runtime counter、benchmark、固定 CPU/allocator/GC 状态或 clean A/B 证据。源码只能支持操作级模型，例如：

```text
一次新 LayoutInfo 分配
+ 旧物理 TaggedArray 长度的复制
+ 新属性写入及读/写屏障
+ HClass/Layout 发布
```

不能据此直接给出纳秒值或总体启动百分比。

方案 B 修改 `ComputeGrowCapacity` 会同时影响 `ExtendLayoutInfo`、`CopyAndReSort` 以及所有默认 GROW 调用点，不能仅根据 LayoutInfo 当前 slack 宣称“覆盖全部路径且低风险”。在没有逐调用点写入闭包和扩容重放前，方案 B 应保持为待验证实验，不应与三条 KEEP 的候选收益相加。

#### P1：V8 对照需要固定版本和调用点证据

“V8 没有统一固定 `+4 descriptor` 规则”的宽结论可以保留。但本文中关于 `MigrateSlowToFast`、`DescriptorArray::Allocate(..., slack=0)`、`TrimDescriptorArray`、`SlackForArraySize` 具体分支和 object-literal cache 行为的断言，必须绑定具体 V8 commit、文件、行号和调用闭包后才能作为竞品事实。V8 的 DescriptorArray slack、Map transition family 和对象实例 in-object slack tracking 仍需与 ArkTS `LayoutInfo` capacity 分层比较，不能把其中一种机制替换成另一种机制。

### 6.3 下一步验证方向：优先源码端

以下顺序用于把候选分析推进到可修改、可回归的状态。前四项完成前，不建议修改 ArkTS VM 的容量策略。

#### S0：冻结源码和文档事实基线

1. 固定 `arkcompiler_ets_runtime` revision、分支、构建配置和 ABI；后续每次源码变化重新记录 revision。
2. 递归枚举所有 `CreateLayoutInfo`、`CreateSLayoutInfo`、`ExtendLayoutInfo`、`CopyLayoutInfo`、`CopyAndReSort` 调用点，区分直接调用、包装调用、测试调用和实际生产调用。
3. 对每个创建点建立稳定 `site_id`，不要使用可能随插入变化的行号作为唯一身份。
4. 明确记录 `properties` 参数的真实语义：当前属性数、固定 schema 宽度、HClass inline capacity、transition family 上限、复制目标或其他含义。

#### S1：完成 LayoutInfo 写入闭包

对每个 `site_id` 逐项登记：

```text
创建函数和调用者
初始 properties / GrowMode / MemSpaceType
所有可达 AddKey / SetPropertyInit 写入
最大写入 offset
只更新 Attr/representation/track type 的容量中性写入
SetLayout 前后的发布顺序
发布后是否仍可到达 AddKey
CopyAndReSort / ExtendLayoutInfo / no-transition 路径
HClass clone、child transition、family root 关系
local/shared/old/semi/read-only heap domain
capacity 不足时的 fallback
```

`LayoutInfo::AddKey` 本身只断言容量并写入，不负责扩容，见 `ecmascript/layout_info-inl.h:332-342`。因此任何 `FINAL_EXACT` 或 `BOUNDED_RESERVE` 结论都必须覆盖所有可能的写入 offset，而不能只查看第一次 `CreateLayoutInfo` 的参数。

#### S2：优先闭合 G1 的真实对象群体

1. 从 `CreateFunctionClass` 的所有生产调用点开始，按 `FunctionKind`、`JSType` 和 `inlinedProps` 建表，重点检查 `builtins.cpp:236-289`、`394-407`、`748-751` 及 `object_factory.cpp:2018-2079`。
2. 反向确认 `NewJSFunction`、`NewJSBuiltinFunction` 等路径是复用环境 HClass 还是重新建立 HClass，重点检查 `object_factory.cpp:1929-1995`。
3. 逐个确认 `length`、`name`、`prototype` 的实际写入闭包，不能使用固定 2 属性模型。
4. 追踪这些 HClass 是否进入 `SetPropertyOfObjHClass`、`AddPropertyToNewHClass`、`Clone`、`TransProto` 或其他 transition 路径。
5. 只有在确认目标是有限的 bootstrap HClass 集合、且发布后无同 backing 追加时，才能进入 `FINAL_EXACT`；否则保留 GROW 或使用带 fallback 的策略。

#### S3：优先闭合 G10 的迁移和 child transition

1. 从 `JSObject::OptimizeAsFastProperties` 追到 `JSHClass::OptimizeAsFastProperties`，确认 `isDictionary` 分支、HClass clone、LayoutInfo 发布和对象属性 backing 发布顺序。
2. 验证 `EntriesCount()` 是否等于迁移事务中的最大 `AddKey` offset+1，检查重复键、枚举顺序和 `indexOrder` 的影响。
3. 追踪迁移后第一条和后续属性添加分别命中 `AddPropertyToNewHClass`、`ExtendLayoutInfo` 还是 `CopyAndReSort`，并确认 child 是否拥有独立 LayoutInfo backing。
4. 将 out-properties 数组分配和属性值迁移纳入迁移事务性能模型，不能把 G10 简化为 LayoutInfo 一次扩容。
5. 源码闭包成立后，G10 才能作为 `BUILD_EXACT_WITH_FALLBACK` 实验入口；第一版保持 `ExtendLayoutInfo` 和 `CopyAndReSort` 的既有 GROW 行为不变。

#### S4：拆分 G11 的 N-API/大对象路径与普通字面量路径

1. 追踪 `ecmascript/napi/jsnapi_expo.cpp:2834` 到 `CreateJSObjectWithProperties` 的完整调用链，确认哪些调用会进入 `CreateLargeJSObjectWithProperties` 或 `CreateLargeJSObjectWithNamedProperties`。
2. 分别审计 `propertyCount <= MAX_LITERAL_HCLASS_CACHE_SIZE` 和大对象分支，记录 HClass root、LayoutInfo、inline capacity 和 transition chain 的关系。
3. 对小对象字面量确认 `GetObjectLiteralRootHClass(literalLength, maxPropsNum)` 中两个参数的独立语义，不能将 `literalLength` 当作最终 LayoutInfo property count。
4. 对普通语言路径补充编译器/运行时调用者和动态属性写入口；不得用“静态类型禁止追加”替代运行时生命周期证明。
5. 在对象群体没有被拆分前，不使用 G11 约 0.6 MiB 或约 15% 快照占比作为收益结论。

#### S5：单独核验已有 KEEP 路径，避免重复计入收益

1. `class_info_extractor.cpp:216-229`、`248-299` 已明确使用 KEEP，应作为现状而不是新的 GROW→KEEP 收益。
2. `js_hclass.cpp:1495`、`1526` 已使用 KEEP，应区分当前形状容量、family 上限和 child transition 使用量。
3. `object_factory.cpp:2085`、`2105` 的默认 class prototype/constructor 路径，应同时核对 LayoutInfo 实际 `NumberOfElements()` 和 HClass `NumberOfProps()`。
4. 任何已使用 KEEP 的路径不得再进入方案 A 的节省总和；PGO family reserve 只有在 root/child 生命周期被证明后才能单独计算。

### 6.4 源码验证完成后的运行时验证

源码闭包完成后，再增加最小侵入式统计，不先改增长算法。建议记录：

```text
site_id
FunctionKind / JSType
initial_requested_properties
initial_physical_capacity
initial_NumberOfElements
AddKey count and maximum offset
post-publication AddKey count
ExtendLayoutInfo count
CopyAndReSort count
copied physical tagged slots
final physical capacity
final NumberOfElements
HClass clone/child/family relation
heap domain and allocation space
```

其中：

1. `G1` 先验证实际 HClass 创建次数和后续追加闭包；
2. `G10` 先验证迁移后的 Extend/Copy 命中率和复制字节；
3. `G11` 先验证 N-API 大对象与普通字面量的调用量和容量分布；
4. `方案 B` 先做离线 replay 或 debug-only 策略试验，记录扩容次数、复制量和最终 slack，不直接修改默认全局增长公式。

最终 A/B 至少需要同时比较：

```text
LayoutInfo shallow bytes
LayoutInfo allocation count
Extend / CopyAndReSort count
copied tagged slots
创建路径延迟
GC 时间和暂停
Region used / committed
RSS / PSS / peak memory
```

快照中的 `3,348,784 B`、`3,106,544 B` 和 `20,662,928 B` 在完成上述路径归因前仍只能作为结构性上界，不能作为物理内存收益或方案放行线。

### 6.5 当前放行建议

在以下条件满足前，不建议按本文第 5.1 节直接提交“三处参数级改动”：

```text
[ ] G1 已确认 HClass/实例数量关系和 FunctionKind 属性闭包
[ ] G10 已确认迁移事务最大 offset、child backing 和 fallback
[ ] G11 已拆分 N-API 大对象、普通字面量和 PGO/AOT 路径
[ ] K1-K7 的已有 KEEP/family reserve 已重新核算
[ ] 快照收益已具备 creation-site 归因，而不是全量 slack 分摊
[ ] 所有纳秒、启动百分比和 MiB 收益数字已替换为实测或明确的公式上界
[ ] V8 对照已固定 revision 并完成调用点级证据核验
[ ] debug/test 下 compact 标记对象的异常追加有 fail-closed 检查
```

当前推荐顺序为：

```text
源码枚举与写入闭包
→ G1/G10/G11 对象群体归因
→ debug-only 运行时计数
→ 离线容量策略 replay
→ clean same-workload A/B
→ 再决定是否修改默认策略
```

本复核只追加审查意见，未修改 ArkTS VM 源码；本目录现有快照和 census 文件也未在本次操作中改写。

### 3. Graphify 定位与源码确认结果

#### 3.1 G1：`CreateFunctionClass` 不是 per-function LayoutInfo

Graphify 定位到：

```text
ObjectFactory::CreateFunctionClass       ecmascript/object_factory.h:L1042
CreateClassFuncHClass                    ecmascript/object_factory.cpp:L5896
CreateApiClassFuncHClass                 ecmascript/object_factory.cpp:L5903
GetHClassByFunctionKind                  ecmascript/object_factory.h:L258
```

源码确认：

1. `CreateFunctionClass` 创建的是 HClass 及其 LayoutInfo，不是每个 JSFunction 实例各自创建 LayoutInfo，见 `ecmascript/object_factory.cpp:2018-2079`。
2. 普通函数实例和内建函数实例通过 `GetHClassByFunctionKind` 取得环境中的 HClass，见 `ecmascript/object_factory.cpp:1929-1995`。因此不能把应用函数声明数量直接乘以 LayoutInfo 单体收益。
3. `JSFunction::LENGTH_OF_INLINE_PROPERTIES` 的实际值为 `3`，见 `ecmascript/js_function.h:258-262`。当 `inlinedProps == DEFAULT_CAPACITY_OF_IN_OBJECTS` 时，`CreateFunctionClass` 调用 `CreateLayoutInfo(3)`，不是主文档示例中的 `CreateLayoutInfo(2)`，见 `ecmascript/object_factory.cpp:2030-2037`。
4. 普通 GROW 模式下该示例的容量应为：

```text
requested = 3
capacity  = 3 + 4 = 7
```

若实际写入 2 个属性，则结构性 slack 为 `5 × 16 B = 80 B`；若实际写入 3 个属性，则为 `4 × 16 B = 64 B`。因此 G1 不能统一写成“固定浪费 64 B”。
5. `CreateFunctionClass` 的写入集合依赖 `FunctionKind`：`length` 必写；非 class constructor 写 `name`；满足 `HasPrototype(kind)` 的路径写 `prototype`；class constructor 有独立的 class prototype 分支，见 `ecmascript/object_factory.cpp:2039-2075`、`ecmascript/js_function.h:365-385`。
6. G1 的 caller 还包括 N-API class function 路径：`CreateClassFuncHClass` 和 `CreateApiClassFuncHClass` 分别见 `ecmascript/object_factory.cpp:5896-5908`，其调用者见 `ecmascript/napi/jsnapi_class_creation_helper.cpp:149-160`。
7. N-API 路径随后继续通过 `AddInlinedPropToHClass` 写入 `name` 和静态属性，见 `ecmascript/napi/jsnapi_class_creation_helper.cpp:161-179`。该 helper 最终进入无 transition 写入路径，见 `ecmascript/js_hclass-inl.h:473-481`。
8. 无 transition 路径对 capacity 只有断言，没有普通扩容 fallback，见 `ecmascript/js_hclass.cpp:397-410`。因此 N-API class HClass 不能按“创建函数类时已写完 1-3 个属性”直接认定为 final exact，必须按完整构建事务的最大 offset 分配并验证。

结论：上一轮把 G1 降级为 source candidate 是正确方向，但主文档仍需补充 `LENGTH_OF_INLINE_PROPERTIES=3`、N-API caller 和无 transition capacity assertion；在这些内容补齐前，G1 不能进入 `FINAL_EXACT`。

#### 3.2 G10：dictionary→fast 只覆盖 `isDictionary=true` 的重建分支

Graphify 定位到两个同名函数：

```text
JSObject::OptimizeAsFastProperties    ecmascript/js_object.h:L807
JSHClass::OptimizeAsFastProperties    ecmascript/js_hclass.h:L460
```

源码确认：

1. `JSHClass::OptimizeAsFastProperties` 只有 `isDictionary` 分支会从 `NameDictionary` 的 `EntriesCount()` 重建 LayoutInfo，见 `ecmascript/js_hclass.cpp:719-753`。
2. `isDictionary=false` 时只 clone HClass，不执行 dictionary entry 到 LayoutInfo 的重建。因此 G10 必须限定为 `isDictionary=true` 分支，不能把两个同名函数的所有调用全部计入。
3. `JSHClass::OptimizeAsFastElements` 会根据对象是否为 dictionary mode 转调 `JSObject::OptimizeAsFastProperties` 或 `JSHClass::OptimizeAsFastProperties`，见 `ecmascript/js_hclass.cpp:334-343`。该入口必须单独统计。
4. `BuiltinsArkTools::ToFastProperties` 也可显式触发上述路径，见 `ecmascript/builtins/builtins_ark_tools.cpp:1249-1265`。这类显式入口不能默认当作普通生产迁移流量。
5. 初始迁移阶段的确是：读取 `EntriesCount()`，按 `indexOrder` 取 key/Attr，设置 offset `i`，逐个调用 `AddKey`，见 `ecmascript/js_hclass.cpp:728-746`。因此 `KEEP(numberOfProperties)` 对该迁移事务具有源码候选依据。
6. 后续新增属性进入普通 `AddPropertyToNewHClass` 时，顺序不匹配走 `CopyAndReSort`，capacity 不足走 `ExtendLayoutInfo`，然后才调用 `AddKey`，见 `ecmascript/js_hclass-inl.h:428-452`。这支持 `BUILD_EXACT_WITH_FALLBACK`，但不支持“迁移后生命周期已经封闭”的结论。
7. 迁移同时创建 out-properties backing 并迁移值，见 `ecmascript/js_object.cpp:477-511`。G10 的完整成本必须包含 dictionary 遍历、HClass clone/发布、LayoutInfo 创建、out-properties 创建和值迁移。

结论：G10 可以保留为优先实验候选，但必须在主文档中写清 `isDictionary=true` 边界、三个入口的调用来源和后续 child transition 的 fallback。未完成这些源码闭包前，不能声称 G10 风险极低或只需一次约 110 ns 的固定代价。

#### 3.3 G11：N-API 大对象、小对象缓存和普通字面量必须彻底分层

Graphify 定位到：

```text
CreateJSObjectWithProperties          ecmascript/object_factory.h:L815
CreateLargeJSObjectWithProperties     ecmascript/object_factory.h:L1082
CreateJSObjectWithNamedProperties     ecmascript/object_factory.h:L817
CreateLargeJSObjectWithNamedProperties ecmascript/object_factory.h:L1085
GetObjectLiteralRootHClass            ecmascript/object_factory.h:L594
SetPropertyOfObjHClass                ecmascript/js_hclass-inl.h:L485
```

源码确认：

1. `ObjectRef::NewWithProperties` 在 `jsnapi_expo.cpp:2815-2848` 构造 descriptor 后调用 `CreateJSObjectWithProperties`；`ObjectRef::NewWithNamedProperties` 在 `jsnapi_expo.cpp:2864-2873` 调用 named-properties 入口。
2. `CreateJSObjectWithProperties` 对小于等于 `MAX_LITERAL_HCLASS_CACHE_SIZE` 的输入，使用 `GetObjectLiteralRootHClass` 和 `SetPropertyOfObjHClass`，见 `object_factory.cpp:5671-5707`。
3. 大于缓存阈值时，才进入 `CreateLargeJSObjectWithProperties`，该路径直接 `CreateLayoutInfo(propertyCount)` 并填充，见 `object_factory.cpp:5710-5747`。
4. named-properties 路径具有相同的“小对象 root/cache”和“大对象直接 LayoutInfo”分支，见 `object_factory.cpp:5784-5849`。
5. 小对象路径的 `SetPropertyOfObjHClass` 首先执行 `FindTransitions`，命中已有 transition 时直接返回已有 HClass；只有未命中时才 clone 并调用 `AddPropertyToNewHClass`，见 `ecmascript/js_hclass-inl.h:485-500`。因此 `propertyCount` 次循环不等于 `propertyCount` 个新 HClass 或新 LayoutInfo。
6. `GetObjectLiteralRootHClass(literalLength, maxPropsNum)` 将两个参数分开使用：cache 按 `literalLength` 索引，首次创建 root 时传入 `maxPropsNum`，见 `object_factory.cpp:4409-4427`。这两个量不能在收益模型中合并。
7. `propertyCount` 是 N-API 调用时的运行时参数，不是普通语言对象字面量必然具有的编译期最终属性数，见 `jsnapi_expo.cpp:2815-2873`。

结论：G11 的标题虽然已经改为 N-API/工厂大对象，但主文档的 4.3、4.4 和 5.1 仍保留对象字面量示例、编译期属性数和通用 `CreateLayoutInfo(N, GROW)` 表述，尚未完成真正分层。G11 仍只能是 source candidate。

### 4. 容量和收益口径复核

#### 4.1 `+4` 是最多 4 个 property-capacity units

源码定义：

```text
LayoutInfo::ComputeGrowCapacity(old_capacity)
    = min(old_capacity + MIN_PROPERTIES_LENGTH, MAX_PROPERTIES_LENGTH)
MIN_PROPERTIES_LENGTH = 4
```

依据：`ecmascript/layout_info.h:30-35`、`87-95`。

因此应统一写为：

```text
最多 4 个 property-capacity units
= 最多 8 个底层 TaggedArray tagged slots
= 最多 64 B/LayoutInfo（按当前 64-bit 物理模型）
```

当接近 `MAX_PROPERTIES_LENGTH` 时，增长会被上限截断，不能把所有 GROW LayoutInfo 都写成固定 64 B 浪费。

### 4. G10 的细化归因

#### 4.1 用户代码先命中 dictionary，不一定马上命中 G10

用户代码示例：

```ts
const config: Record<string, number> = {};
config.alpha = 1;
config.beta = 2;
delete config.alpha;
config.gamma = 3;
```

删除 named property 的路径进入：

```text
JSObject::DeletePropertyInternal
    -> JSObject::TransitionToDictionary
```

位置：

```text
ecmascript/js_object.cpp:646-667
ecmascript/js_object.cpp:185-244
```

这一步只是把对象转入 dictionary mode，并不等于已经执行 dictionary→fast LayoutInfo 重建。

G10 只有在后续调用：

```text
JSObject::OptimizeAsFastProperties
    -> JSHClass::OptimizeAsFastProperties(..., isDictionary=true)
```

时才命中 LayoutInfo 重建分支，见：

```text
ecmascript/js_object.cpp:477-511
ecmascript/js_hclass.cpp:719-753
```

因此用户代码应分两段归因：

```text
delete/redefine/attribute mutation -> dictionary transition
显式或 VM 内部 fast-property optimization -> G10
```

不能用 dictionary 对象数量直接替代 G10 调用次数。

#### 4.2 G10 的真实分支

`JSHClass::OptimizeAsFastProperties` 的核心分支为：

```cpp
newJsHClass = Clone(thread, jshclass, isDictionary);

if (isDictionary) {
    numberOfProperties = properties->EntriesCount();
    layoutInfo = CreateLayoutInfo(numberOfProperties);
    for (i = 0; i < numberOfProperties; i++) {
        ...
        layoutInfo->AddKey(...);
    }
    newJsHClass->SetNumberOfProps(numberOfProperties);
    newJsHClass->SetLayout(thread, layoutInfo);
}
```

位置：

```text
ecmascript/js_hclass.cpp:719-753
```

只有 `isDictionary=true` 才创建新的 LayoutInfo。`isDictionary=false` 只 clone HClass，不应计入 G10 的 LayoutInfo 重建数量。


该路径创建 `NameDictionary`，不是 fast LayoutInfo。其容量浪费应按 dictionary hash-table 的容量、空桶、删除项和 rehash 规则另行分析，不能加入 G11 的 LayoutInfo slack。

### 6. 统一容量账本

本轮建议所有路径采用以下账本字段：

```text
site_id
user_entry
creator
branch_condition
FunctionKind / JSType
requested_properties
requested_semantics
initial physical capacity
actual AddKey count
maximum AddKey offset
post-publish AddKey count
ExtendLayoutInfo count
CopyAndReSort count
transition cache hit/miss
HClass clone count
LayoutInfo pointer identity
final physical capacity
final NumberOfElements
HClass NumberOfProps
heap domain / allocation space
```

容量计算统一为：

```text
capacity(GROW) = min(requested_properties + 4, MAX_PROPERTIES_LENGTH)
capacity(KEEP) = requested_properties
slack_units = max(physical_capacity - effective_property_count, 0)
slack_bytes = slack_units × 16 B
```

其中 `effective_property_count` 必须明确是：

```text
LayoutInfo::NumberOfElements()
```

还是：

```text
当前 HClass::NumberOfProps()
```

两者在 transition family 场景中不能默认视为相等。

### 7. 归档建议和下一步放行条件

#### 7.1 当前可以归档为源码事实的内容

```text
CreateFunctionClass 创建 HClass，不是每个 JSFunction 实例的 LayoutInfo
JSFunction::LENGTH_OF_INLINE_PROPERTIES = 3
FunctionKind 决定 length/name/prototype 写入集合
N-API class function/prototype 存在额外无 transition 写入
无 transition 路径没有普通 Extend fallback
G10 LayoutInfo 重建只发生在 isDictionary=true 分支
OptimizeAsFastElements 还涉及 Elements 路径
ArkTools::ToFastProperties 是显式入口
G11 大对象 direct path 的 propertyCount 是运行时输入
G11 小对象 path 经过 root/cache/transition，不等于 direct LayoutInfo 分配
超过 fast 上限的 G11 path 进入 dictionary
```

#### 7.2 当前仍不能归档为已验证收益的内容

```text
G1/G10/G11 各自的快照对象数量
G1/G10/G11 各自的 MiB 收益
G1/G10/G11 各自的后续追加概率
统一 64 B/LayoutInfo 的实际可回收收益

RSS/PSS、Region committed 或冷启动收益
```

#### 7.3 继续验证的源码优先顺序

```text
1. 修正 G1 的 NORMAL_FUNCTION / BASE_CONSTRUCTOR / CLASS_CONSTRUCTOR 分支表
2. 把 G1-B/G1-C 的 N-API 完整事务最大 offset 独立建表

7. 以 site_id 加 debug-only counters
8. 用 counters 归因快手前台/后台和 TOP13 快照
9. 完成 offline replay 后再决定 KEEP 参数
10. 最后做 clean same-workload A/B
```

当前不建议修改全局 `ComputeGrowCapacity`，也不建议把 `CreateFunctionClass`、dictionary→fast 和 N-API 大对象三个入口分别直接改成 KEEP。应先完成上述子路径账本，避免把 HClass 数量、JSFunction 实例数量、transition family 数量和 LayoutInfo 物理对象数量混为一谈。
