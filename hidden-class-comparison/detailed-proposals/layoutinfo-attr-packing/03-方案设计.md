# LayoutInfo 属性描述槽压缩 —— 方案设计（按架构特性设计模板）

## 1、特性需求/问题/动机的来源与价值

**问题来源**：Top13 复算发现 LayoutInfo 数组合计 109.25 MiB（735,734 个去重对象），是 JSHClass 本体（68.78 MiB）的 1.59 倍。每属性以 Key 8 B + Attr 8 B 交织存放，而 Attr 是 uint32 位域以 Smi 编码占满整槽——每属性 4 B（25%）为纯浪费。

**价值**：Attr 区 4 B 原始编码后每属性 16 B → 12 B，Top13 全量逐数组精算（含 8 B 对齐）节省 **23.17 MiB / 21.2%**；与 JSHClass AuxData Sidecar（17.7 MiB）同对象族不同数组、收益可叠加、版本契约可同批。

**实现前 vs 实现后（用户视角）**：实现前每个 shape 的属性描述占 16 B/属性；实现后 12 B/属性，属性查找、transition、枚举、序列化行为完全不变。

## 2、特性影响分析

### 2.1 系统位置

对象模型核心（JSHClass → LayoutInfo 属性查找链），影响属性访问、对象创建/transition、枚举、AOT 编译偏移、GC visitor、序列化与快照工具。

### 2.2 环境依赖

- 无档位/多 target 差异（64 位布局，对 JIT/AOT-off 分档无感知）；
- 单一布局，不允许新旧交织混堆。

### 2.3 涉及模块

`layout_info{.h,-inl.h,.cpp}`、`js_hclass` 查找链与 transition、GC visitor/write barrier（仅 Key 区）、serializer、heap snapshot/rawheap metadata、`js_metadata_test`、AOT 编译偏移与 `.an/.ai` 版本。

### 2.4 前后版本兼容性

- 不改变公开 API、字节码格式、JSHClass/JSFunction 布局（**JSFunction 布局冻结约束不受影响**）；
- LayoutInfo 元素偏移是 ArkVM 内部编译契约（AOT `LookupPropertyInAotHClass` 固定偏移读取）：bump `.an/.ai` 版本 + strict match 拒绝旧产物、clean rebuild；rawheap metadata 同步，旧 translator 对新 rawheap 因版本不匹配失败。

### 2.5 外部用户感知

无（属性语义、枚举顺序、序列化结果不变）。

### 2.6 性能影响

- 时间：Attr 读取从「交织 +1 槽」改为「同下标另一区首址 + 4B 步进」，均为一次额外加法；查找链微基准与 IC 全状态回归设 ≤1% 阈值；
- 空间：−23.17 MiB（Top13 浅层精算）；GC 扫描槽减半（Attr 区不再作为 tagged 槽）。

## 3、业界竞品分析

| 引擎 | 对应结构 | 做法 |
|---|---|---|
| V8 | `DescriptorArray` | key/details 分列存放，details 为紧凑位域；数组跨 Map 共享 |
| JSC | `PropertyTable` | key/attributes 分列，attributes 紧凑编码 |
| ArkVM（现状→本方案） | `LayoutInfo` | 交织 Key/Attr 双 tagged 槽 → 分离双区（Key tagged + Attr raw u32） |

本方案即向竞品的「分列 + 紧凑位域」形态靠拢；跨 hclass Layout 共享（V8 DescriptorArray 共享）受 transition 前缀共享天然上限（0.898）约束，另行评估。

## 4、本特性的设计/实现方案

### 4.1 目标布局（分离双区）

```text
现状（交织，每属性 16 B）             目标（双区，每属性 12 B）
header 16 B                          header 16 B
key0  attr0  key1  attr1  …          key0  key1  key2 …   （8 B tagged 区）
                                     attr0 attr1 attr2 …   （4 B raw u32 区）
```

尺寸公式：`ComputeSize = align8(DATA_OFFSET + 8×N + 4×N)`。编址：`KeyIndex(i) = DATA_OFFSET + 8i`、`AttrIndex(i) = DATA_OFFSET + 8N + 4i`；长度字段单一来源（N），heap verification 断言两区边界。

**不采用交织 12 B/属性**：Attr 地址按 12 B 步进交错，编译侧与循环展开不友好；双区使 Attr 区成为连续 u32 数组，「Key 区查找 + Attr 区同下标读取」与现状访问模式差异最小（ADR 已定）。

**不进一步打包至 2 B**：`PropertyAttributes` 的 uint32 语义被序列化/调试直接消费，换算成本高于增量收益（~12 MiB）。

### 4.2 访问器与 GC

- `GetAttr/SetAttr` 走 `GetPrimitive` 类 raw 访问（`ACCESSORS_FIXED_SIZE_FIELD` 先例）；`GetKey/SetKey` 维持 tagged 访问与 write barrier；
- visitor 只扫 Key 区（现状 Attr 是 Smi、扫描时天然跳过，语义等价）；moving GC 只更新 Key 槽；
- Attr 为 raw，无屏障、无扫描——Attr 区末尾后放置哨兵对象的压力 GC 用例验证不被覆写/误扫。

### 4.3 查找链迁移

`LookupProperty*` 五入口（fast/prototype/builtin/AOT/PGO）与 transition 追加路径、`GetAllKeys/GetAllEnumKeys` 枚举路径统一改双区编址 helper；AOT 侧固定偏移读取随 `.an/.ai` 版本同步重生成。

### 4.4 与 AuxData Sidecar 同批实施

两项都触碰 hclass 内部契约：合并 bump 一次版本、一次 clean rebuild、一套新旧产物拒绝测试；实现顺序无依赖（不同数组），建议同一 AR 序列分两个 PR 上库，工具链改动共享。

### 4.5 方案利弊

| 方案 | 优点 | 代价 |
|---|---|---|
| **分离双区 4 B Attr（选）** | 精算 23.17 MiB；编址简单；GC 语义等价 | 内部契约版本 bump；查找链全量迁移 |
| 交织 12 B/属性 | 同收益 | 地址交错，编译侧改造面更大 |
| 位打包 2 B | ~35 MiB | uint32 语义被直接消费，换算成本高 |
| 跨 hclass Layout 共享 | 上限 ~10% | transition 已天然共享前缀，增量小 |

## 5、DFX 分析

- 可诊断性：dump/快照按 Key+Attr 逻辑视图输出属性表；rawheap metadata 同步新偏移；
- 可运维性：版本不匹配拒绝加载（沿用 `.an/.ai` strict match）；
- 可测试性：见第 7 节与需求 §5。

## 6、可信分析

- **可靠性**：GC 扫描区间收窄经 heap verification 与哨兵用例验证；两区长度一致性由单一来源 + 断言保证；
- **安全性**：不涉及输入解析/权限；**隐私/无害**：不涉及（内部布局改造）。

## 7、关键 DT 用例简述

| 测试用例名称 | 预置条件 | 用例关键步骤 | 预期结果 |
|--------------|----------|--------------|----------|
| 尺寸公式 | 双区布局构建 | 构造 N=1..33 的 Layout | `size == align8(16+12N)` |
| 属性查找全路径 | fast/dict/原型/AOT/PGO | 增删改查 + 枚举顺序 | 与现状逐字节一致 |
| Attr 区哨兵 | Layout 后放哨兵对象 | 压力 GC | 哨兵不变、无越界写 |
| 新旧产物互拒 | 旧 AOT + 新 runtime | 加载 | 稳定拒绝 |
| Lookup 性能 | 微基准 + IC 全状态 | 前后对比 | 回退 ≤1% |
| Top13 A/B | 双版本快照 | 逐数组 self_size | 降幅 ≥20 MiB 且符合公式 |

## 8、结论

方案设计完成，按「分离双区 + 4 B raw Attr」实施；与 AuxData Sidecar 同批版本 bump。遗留问题见 `04-review-log.md`。
