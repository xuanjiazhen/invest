# 应用侧内存改造端到端指导（A1–A6）

面向应用开发者的实操手册：每项按**识别 → 风险评估 → 改造方案 → 验证**四步给出端到端流程。识别步骤均以本仓库脚本 + 快照特征或源码模式定位；文末附「AI 辅助改造」的执行规程（可直接交给 AI agent 按应用源码执行）。

前置准备（所有项目通用）：

```bash
# 1. 采集基线快照（设备端）
hdc shell hidumper -s 1908 -a "-d <pid> rawheap"   # 或 DevEco Profiler 内存快照
# 得到 .rawheap 后用 SDK rawheap_translator 转成 .heapsnapshot
# 2. 基线指标记录：PSS（hidumper meminfo <pid>）+ 下文各项目的目标节点指标
```

## A1 native 类注册去重

**识别**：跑 `python scripts/class_copy_census.py <app>.heapsnapshot`——输出「同一 native 类的 prototype 拷贝数」。拷贝数 >1 即存在重复注册（健康值 = 1；同 class 多 global_env 场景见 A2）。源码侧特征：`napi_define_class` 出现在可被多次执行的初始化路径（构造函数、getter、模块内函数）而非模块顶层一次性执行。

**风险评估**：低。去重只影响「第二份及以后」的注册，首个注册行为不变；唯一注意点是依赖「每次注册产生新类对象」的测试用例（`instanceof` 判定跨副本不一致本就是缺陷）。

**改造方案**：把 `napi_define_class` 移到模块作用域一次执行并缓存：

```cpp
// 改造前：initClass() 每次调用都 define（常见于懒加载 getter 内）
static napi_value InitFoo(napi_env env, napi_value exports) {
    napi_value cls = NapiDefineClass(env, "Foo", ..., nullptr, 0, nullptr);  // 重复执行
    ...
}

// 改造后：模块加载时注册一次，后续直接取
static napi_ref fooClassRef = nullptr;
static napi_value InitFoo(napi_env env, napi_value exports) {
    if (fooClassRef != nullptr) { return GetFromRef(env, fooClassRef); }
    napi_value cls = NapiDefineClass(env, "Foo", ..., nullptr, 0, nullptr);
    napi_create_reference(env, cls, 1, &fooClassRef);
    ...
}
```

完整缺陷模式与逐应用案例见 `../../lazy-binding-app-side-guide.md` §2、§4。

**验证**：改造后重跑 `class_copy_census.py`，目标类拷贝数降为 1；`instanceof` 行为回归；PSS 不回退。

## A2 系统模块（@ohos.*）惰性导入

**识别**：跑 `python scripts/measure_lazy_binding_targets.py <app>.heapsnapshot`——W-sys 按模块分布表给出「该模块 prototype 闭包 MiB」；MiB 大且业务上仅后台/少数路径使用的模块为候选。源码侧：全局 `import ... from '@ohos.xxx'` 且模块能力只在部分页面/分支使用。

**风险评估**：中。三个注意点：① 首次访问引入加载延迟（冷路径可接受，热路径勿改）；② getter 形态与数据属性的 descriptor 语义不同——不得对会被 `Object.freeze`/`getOwnPropertyDescriptor` 扫描的对象使用；③ 避免循环依赖时段的读取。

**改造方案**（自替换 getter，类型安全写法见 `../../lazy-binding-app-side-guide.md` §3.4–3.5）：

```ts
// 改造前
import { bundleManager } from '@kit.AbilityKit';   // 模块加载即全量注册 native 类

// 改造后
let bundleManagerRef: typeof import('@kit.AbilityKit').bundleManager | undefined;
export function getBundleManager() {
    if (bundleManagerRef === undefined) {
        ({ bundleManager: bundleManagerRef } = require('@kit.AbilityKit'));
    }
    return bundleManagerRef;
}
```

三个反模式（模块内立即执行的使用、顶层 await、被 freeze 的对象）见指南 §3.6。

**验证**：两版快照对比 W-sys 该模块 prototype 闭包消失；冷启动 P50/P95 与首次访问延迟实测；期望收益按 VM 侧 probe 数据（`detailed-proposals/native-interop-lazy-binding/05-插桩patch.md`）折算。

## A3 逐实例方法绑定提升为 prototype

**识别**：跑 `python scripts/detect_native_interop_dup.py <app>.heapsnapshot`——输出非 prototype 持有的同 hclass 冗余闭包（Top13 合计 1.39 MiB）。源码特征：在实例构造路径上 `obj.method = function...` / `napi_define_properties` 逐实例注入同名方法。

**风险评估**：低-中。方法上移后为原型共享，`hasOwnProperty('method')` 由 true 变 false（依赖此判定的代码需排查）；实例级闭包捕获（引用实例变量）不可上移。

**改造方案**：

```ts
// 改造前
class Node { constructor() { this.hashCode = () => computeHash(this); } }  // 每实例一份

// 改造后
class Node { hashCode() { return computeHash(this); } }                    // prototype 一份
```

**验证**：`detect_native_interop_dup.py` 冗余桶归零；`hashCode in obj` 与 `obj.hasOwnProperty('hashCode')` 按预期调整后的用例回归。

## A4 dynamic-key 场景改用 Map/Set

**识别**：快照中 `tagged_dictionary` 节点数与字节（Top13 21,268 个 / 32.19 MiB，平均 1,587 B）；单应用 >100 个或单对象 >4 KB 为强信号。源码特征：`obj[dynamicKey] = v`、`delete obj[key]`、以对象作键值容器。

**风险评估**：低。Map/Set 与普通对象在迭代顺序、JSON 序列化上不同——有 `JSON.stringify(obj)` 直接输出的容器需保留对象形态或加序列化适配。

**改造方案**：

```ts
// 改造前
const cache: Record<string, Item> = {};
function touch(k: string) { cache[k] ??= load(k); if (rare) delete cache[k]; }

// 改造后
const cache = new Map<string, Item>();
function touch(k: string) { if (!cache.has(k)) cache.set(k, load(k)); if (rare) cache.delete(k); }
```

**验证**：快照 `tagged_dictionary` 数量/字节下降；缓存行为（命中/淘汰）回归。

## A5 响应式装饰器精简

**识别**：快照 `property_box`/`cell_record`/`js_weak_ref` 节点数（Top13：PropertyBox 97,568 / get-set 对 13,651 / WeakRef 57,288）。源码特征：`@State/@Prop/@Link` 标注在**不被 UI 绑定引用**的字段上（纯计算中间量、仅内部同步的状态）。

**风险评估**：中。**仅精简确认无 UI 绑定的字段**；被 `$$/` 双向绑定、`@Watch`、Builder 内引用的字段不可动。建议按「字段名未出现在任何 `build()`/Builder/UI 布局表达式」判据筛选，逐字段回归。

**改造方案**：

```ts
// 改造前
@Entry struct Page {
  @State pageIndex: number = 0;      // UI 绑定，保留
  @State rawBuffer: number[] = [];   // 无 UI 绑定的计算中间量
}

// 改造后
@Entry struct Page {
  @State pageIndex: number = 0;
  rawBuffer: number[] = [];          // 普通类字段，不生成响应式包装
}
```

**验证**：快照三类节点数下降；逐页面 UI 回归（重点：精简字段的派生计算结果不变）。

## A6 大字符串（>1K）缓存治理

**识别**：快照 string 节点（注意：`self_size` 是字符长度，>1024 即候选）按持有者归因——集中在少数模块的（Top13 >1K 数据合计 32.63 MiB，pinduoduo/jingdong/gaodeditu 高度集中）。持有边特征：`other:native`/`tagged_array` 下的 MB 级 string。

**风险评估**：低-中。缓存内容被复用才有价值；一次性拼接大串（日志、请求体）应改流式处理而非缓存。

**改造方案**：大缓存改 LRU + 容量上限（`util.LRUCache` 或自实现）；>256 KB 的拼接产物避免多次中间串（用数组 join 一步完成）；只读大常量串考虑资源文件 + 按需读取。

**验证**：>1K string 总字节下降；PSS 对应下降；缓存命中率不低于改造前。

## AI 辅助改造执行规程（可 skill 化）

交给 AI agent 按应用源码执行的固定流程（对应 TODO 中「skill 基于应用源码进行指导改造」）：

1. **输入**：应用源码目录 + 一份 `.heapsnapshot` 基线（可选，有则先跑上述脚本得热点排序）。
2. **静态扫描**（按优先级，逐项输出候选清单：文件:行号 + 命中模式）：
   - A1：`napi_define_class` 出现在非模块顶层执行路径（函数体/getter/构造内）；
   - A2：`import ... from '@ohos.'` 且模块标识符仅在 ≤20% 文件中被引用（可用引用计数近似）；
   - A3：构造函数/初始化器内 `this.<name> = (function|箭头函数)` 且函数体未捕获实例状态；
   - A4：`delete <obj>[` 与 `obj[<变量>] =` 组合出现 ≥3 次的容器对象；
   - A5：`@State|@Prop|@Link` 字段名未出现在任何 `build(` 体内；
   - A6：`字符串常量长度 > 1024` 或 MB 级数组 join。
3. **逐候选风险评估**（按上文各项风险条款，输出「可改/需人工确认/不改」三分类及理由）。
4. **改造**：对「可改」项按上文模板生成 patch（保持代码风格，不做无关重构）。
5. **自检**：引用完整性（改动的导出仍被正确引用）、类型检查（`hvigor` 编译）、反模式复查（A2 的三个反模式逐条过）。
6. **输出报告**：每项 候选数/已改数/风险跳过数 + 改造前后快照对比表（有快照时）。

人工验收：编译通过 + UI 冒烟 + 快照指标复测（各项目的验证小节）。
