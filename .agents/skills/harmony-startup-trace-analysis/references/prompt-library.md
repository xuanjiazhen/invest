# GLM-5.2 专业提示词库

使用时替换尖括号变量。不要把完整 Trace 放入提示词；只提供 schema、查询摘要和少量证据行。

## 1. 脚本能力审计

```text
你是鸿蒙应用启动性能 Trace 分析工程师。请审计下面的内部解析脚本接口和样例输出，不要开始判断性能问题。

分析目标：<包名/进程名>，启动类型=<类型>，关注相对区间=<0s-8s>。
脚本帮助/接口：<内容>
输出字段定义：<内容>
小窗口样例：<内容或路径>

请输出：
1. 能可靠回答的问题；
2. 缺失或可能失真的字段；
3. 聚合、截断、去重、时间精度和关联关系风险；
4. 每项风险的最小验证查询；
5. 需要从原始 Trace 通过脚本补取的数据。

约束：脚本输出只是线索；不得把“字段未出现”解释为“事件不存在”；不确定项标记“未知”。
```

## 2. 生成最小查询计划

```text
基于以下 Trace schema 和当前问题，只设计下一轮最小查询，不输出性能结论。

问题：<要验证的单一问题>
目标进程/PID：<值>
关注时间窗：<绝对和相对时间>
可用表/事件/字段：<schema摘要>
已有证据：<E-ID摘要>

输出：
- 查询目的；
- 所需字段及原因；
- 精确过滤条件；
- SQL/命令伪代码或可执行查询；
- 预期结果的三种分支及各自下一步；
- 查询不能证明什么。

必须限制时间窗和目标进程，避免全表导出。结果应保存到文件。
```

## 3. 启动时间线重建

```text
请根据提供的结构化查询结果重建启动时间线。只使用输入中能核验的事件，不用平台常识填补空白。

启动口径：<触发点与完成点>
进程/线程映射：<内容>
事件摘要：<内容>
字段定义：<内容>

输出表：阶段、起始事件、结束事件、相对起止、墙钟耗时、执行主体、前驱、后继、证据ID候选、未知项。

规则：
- 不累加重叠线程耗时；
- 区分执行、Runnable、Sleeping、I/O、锁和IPC等待，仅使用实际可用状态；
- 无法确认依赖时写“时间相关，因果未证”；
- 标出需要二次查询的时间空洞。
```

## 4. 候选瓶颈证据审查

```text
审查候选问题 <候选ID/描述> 是否足以认定为启动瓶颈。

启动完成点：<内容>
主证据：<结构化证据>
关联证据：<结构化证据>
交叉验证：<内容>
候选反证：<内容>

按以下格式输出：
1. 可确认事实；
2. 从事实到完成点延迟的逐跳影响链；
3. 因果链缺口；
4. 可能推翻结论的反证；
5. 结论等级：已确认问题/观察项/证据不足；
6. 可信度：高/中/低及理由；
7. 下一条最小补证查询。

禁止仅凭耗时长、事件名或经验认定瓶颈。
```

## 5. 系统侧分析

```text
请从系统侧审查时间窗 <范围>，目标是解释应用关键线程为何没有推进，不是罗列系统事件。

关键线程状态：<内容>
调度/CPU摘要：<内容>
IPC与系统服务摘要：<内容>
内存/缺页/I/O摘要：<内容>
图形链路摘要：<内容>

分别检查：调度等待、CPU竞争/频率、IPC对端、内存回收/缺页、存储、图形合成、系统服务排队。
每类输出：已观察事实、与关键线程的时间对齐、是否处于关键路径、证据ID、反证、缺失轨道。
缺少轨道时明确写“无法判断”，不得推断。
```

## 6. 应用侧分析

```text
请从应用侧审查时间窗 <范围>，判断哪些工作直接推迟 <启动完成点>。

主线程切片：<内容>
工作线程切片：<内容>
生命周期/首帧事件：<内容>
I/O、锁、IPC摘要：<内容>

检查：主线程长任务、同步初始化、首帧前非必要候选工作、I/O、锁、IPC、重复初始化、UI构建和渲染。
每项必须给出：事件与线程、起止时间、阻塞的后继事件、证据ID、当前不能证明的业务必要性、补充源码/插桩需求。
禁止在没有源码证据时指定具体函数改法。
```

## 7. 事实报告生成

```text
根据证据账本生成“事实与问题描述”。只能引用账本中的 E-ID，不得提出优化建议。

输入清单：<内容>
启动时间线：<内容>
证据账本：<内容>

要求：
- 说明启动起止口径和总耗时；
- 每个问题分配 F-ID；
- 每个陈述引用 E-ID；
- 写清影响链、归属层级、可信度和证据边界；
- 证据不足项放入“待验证观察”，不得混入已确认问题；
- 不出现“应该优化、建议、可改为”等建议措辞。
```

## 8. 优化方向生成

```text
根据已确认事实生成“可能的优化方向”，不得产生无法追溯到 F-ID/E-ID 的建议。

事实问题：<F-ID列表>
证据账本：<相关E-ID>
已知源码/平台约束：<内容或未知>

每条方向分配 O-ID，并输出：关联F-ID/E-ID、适用层级、候选动作、作用机制、前置条件、风险、最小实验、成功指标、回归指标、复采Trace预期。

规则：
- 使用“可能、候选、需实验验证”，不承诺收益；
- 区分应用可执行、平台需处理、采集环境需控制；
- 没有源码依据时只描述机制，不编造函数或模块；
- 无清晰证据链的方向不输出。
```

## 9. 最终证据一致性审计

```text
审计以下事实报告、优化方向和证据账本的一致性。

证据账本：<内容>
事实报告：<内容>
优化方向：<内容>

逐项列出：
- 无E-ID支持的事实；
- 无F-ID/E-ID支持的建议；
- 引用不存在或字段冲突；
- 时间口径、单位、PID/TID、启动类型不一致；
- 把相关性写成因果性的句子；
- 重叠耗时重复相加；
- 把“未查询到”写成“不存在”；
- 建议中的收益承诺或遗漏验证实验。

只输出审计问题和修复要求，不重写报告。
```
