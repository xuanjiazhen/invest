# 启动 Trace 分层分析手册

本手册提供查询方向，不把平台常识当成当前样本事实。任何具体判断都必须回到 Trace 证据。

## 一、先判定关键路径

对每个启动阶段记录：

| 字段 | 含义 |
|---|---|
| 起止事件 | 可回查的事件名与时间戳 |
| 执行主体 | PID、TID、线程名、系统服务 |
| 前驱/后继 | 哪个事件触发它，哪个里程碑等待它 |
| 墙钟耗时 | 起止差值，不与重叠线程直接求和 |
| 状态构成 | Running、Runnable、Sleeping、I/O、锁、IPC 等；以实际 schema 为准 |
| 关键性 | 是否推进启动完成点 |

判断重点不是“谁最慢”，而是“谁推迟了目标完成点”。并行后台任务即使耗时长，也可能不在关键路径。

## 二、应用侧候选模式

### 主线程长任务

查证：主线程连续切片、CPU running 时间、调度等待、后继生命周期或首帧事件。

区分：

- 真正执行时间长；
- Runnable 但未获 CPU；
- Sleeping 等待锁、I/O 或 IPC；
- 父切片长但内部异步工作并未阻塞。

### 首帧前同步初始化

查证：初始化切片与首帧/页面完成的先后依赖、调用或父子关系、是否可见页面必需。

不能仅凭名称断言可延迟。业务必要性需要源码、产品口径或实验补证。

### 文件与资源 I/O

查证：文件访问、缺页、I/O wait、资源加载事件、调用线程及后继等待。

区分实际磁盘等待、页缓存命中、CPU 解码/解析和锁等待；不要统一归为 I/O 慢。

### 锁与线程同步

查证：等待线程、持锁线程、等待区间、唤醒关系、关键线程后继事件。

若 Trace 不含锁所有者，只能报告等待现象，并提出补充插桩或采集方案。

### IPC/Binder

查证：请求端发起、事务标识、对端 PID/TID、服务端处理、回复、客户端恢复执行。

端到端耗时至少拆分：客户端调度、传输/排队、服务端调度、服务端执行、返回等待。不能把全部时间归责于服务端。

### UI 构建与渲染

查证：页面生命周期、布局/测量/绘制、渲染提交、合成与显示事件，以及主线程/渲染线程的依赖关系。

“首帧提交”与“屏幕显示”可能不是同一完成点，报告必须说明口径。

## 三、框架与运行时候选模式

仅当 Trace 事件或平台文档能确认时，分析以下阶段：

- 进程孵化、创建或恢复；
- 运行时、模块、动态库或字节码加载；
- Ability 生命周期和UI框架初始化；
- GC、JIT、AOT或解释执行相关事件；
- 资源管理、路由和页面创建。

检查这些阶段是否位于目标应用关键路径，以及时间是执行、调度还是等待。平台组件中的长耗时不自动等于平台缺陷。

## 四、系统侧候选模式

### CPU 调度与竞争

查证：关键线程 Runnable 时间、实际 Running 时间、CPU 迁移、优先级、同核竞争者。

若关键线程大量 Runnable 等待，进一步识别竞争进程和采集环境负载。单看 CPU 利用率不足以证明调度瓶颈。

### CPU 频率与热约束

查证：关键区间 CPU 频率、idle 状态、调度落核、温控或限频事件。缺少相关轨道时不得推断降频。

### 内存、缺页与回收

查证：minor/major fault、reclaim、内存压力、进程 RSS 变化及其与关键线程停顿的时间关系。

缺页数量不是影响证据；还需证明其发生在关键线程或关键依赖服务上，并推迟后继事件。

### 文件系统与存储

查证：块 I/O、文件系统调用、队列和完成事件。需要区分应用直接 I/O、动态加载、资源读取及系统服务代办。

### 图形与合成链路

查证：应用提交、渲染服务接收、合成、VSync 和显示相关事件。确定延迟发生在应用未提交、系统排队、错过 VSync 还是显示完成阶段。

### 系统服务

查证：请求到达、排队、处理、依赖调用和回复。将系统服务耗时与客户端等待区间对齐，排除无关并行请求。

## 五、反证清单

每个候选问题至少检查一项：

- 同一事件是否与关键路径并行且结束早于完成点依赖；
- 关键线程是否实际在等待该事件；
- 相同长事件是否也出现在正常样本且不影响完成点；
- 聚合耗时是否由大量重叠事件重复计算；
- 线程名、PID 或事务关联是否匹配错误；
- Trace 丢事件、截断或采样是否造成假空洞；
- 完成点选择变化后，该候选是否仍位于关键路径；
- 该现象是否可能来自调试构建、采集开销或后台负载。

## 六、优化验证设计

每个方向只改变一个主要变量，至少记录：

- 基线与实验版本、设备、系统版本、启动类型和采集配置；
- 清缓存、重启、温度、网络和后台负载控制方式；
- 多次重复结果，报告分布而非只报最好值；
- 主指标：相同口径下的启动完成时间与目标阶段耗时；
- 回归指标：首帧正确性、可交互性、内存、CPU、功耗、稳定性；
- 新 Trace 中预期消失、缩短或后移的事件。

实验结果与预期不符时，回退优化结论，保留原证据和实验记录。
