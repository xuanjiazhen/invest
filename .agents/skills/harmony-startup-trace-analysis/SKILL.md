# 鸿蒙应用启动 Trace 证据化分析

## 目标

对应用启动 Trace 做可复核定位，而不是仅按耗时排序。最终交付必须严格分为：

1. **事实与问题描述**：只写 Trace 或辅助材料能够直接证明的现象、时序、耗时和影响。
2. **可能的优化方向**：基于已确认事实提出候选动作，明确适用层级、验证方法和不确定性。

每个问题和每条优化方向都必须引用证据 ID。没有证据，不得下结论。

## 硬性约束

- 不直接读取、粘贴或加载完整原始 Trace。100MB 以上文件只能由脚本、查询引擎或流式工具处理。
- 默认只分析从启动基准点开始的 `0s-8s`；区间外数据除非用于建立必要因果边界，否则忽略并说明理由。
- 已有脚本输出是线索，不是事实终点。必须抽样回查原始 Trace 或使用第二种查询交叉验证关键结果。
- 不把相关性写成因果性。不因某事件“耗时长”就直接认定它阻塞启动。
- 不凭名称猜线程、阶段或业务含义。无法确认时标记 `未知`，列出补证方式。
- 事实、推断、建议分栏表达。禁止把建议混入事实章节。
- 保留每一步使用的命令、参数、输入摘要、输出路径、观察结果和下一步决策。
- 原始 Trace 只读；所有中间产物写入独立分析目录。

## 输入契约

开始前收集；缺失项不得臆造：

| 字段 | 必需 | 说明 |
|---|---:|---|
| Trace 路径 | 是 | 原始文件只读，记录文件大小与哈希 |
| 应用标识 | 是 | 包名、进程名、PID 线索至少一个 |
| 启动类型 | 是 | 冷启动、热启动、温启动或未知 |
| 启动触发点 | 否 | 点击、Ability 启动请求、进程创建等可定位事件 |
| 完成点 | 否 | 首帧、可交互、业务首页完成等；必须说明口径 |
| 已有脚本 | 否 | 路径、用法、输出字段、已知缺口 |
| 设备上下文 | 否 | 机型、系统版本、构建类型、负载状态、采集配置 |
| 对照样本 | 否 | 正常/历史/竞品 Trace，需保证口径可比 |

若启动类型或完成点未知，先执行探索查询，不得提前计算“启动总耗时”。

## 产物目录

在用户指定位置或 `<trace目录>/startup-analysis-<时间戳>/` 创建：

```text
00-input-manifest.md
01-tool-capability.md
02-analysis-log.md
03-evidence-ledger.md
04-factual-findings.md
05-optimization-directions.md
queries/
extracts/
```

- `00-input-manifest.md`：输入、哈希、分析区间、启动口径、环境元数据。
- `01-tool-capability.md`：已有脚本能力、字段覆盖、限制和补充查询方案。
- `02-analysis-log.md`：逐步命令与决策记录，追加写，不覆盖历史。
- `03-evidence-ledger.md`：唯一证据账本，所有结论从这里引用。
- `04-factual-findings.md`：事实与问题描述。
- `05-optimization-directions.md`：可能的优化方向与验证实验。

模板见 [report-templates.md](./references/report-templates.md)。

## 执行流程

### 1. 建立输入清单与保护边界

1. 记录文件路径、大小、修改时间、哈希，不复制完整文件内容到上下文。
2. 明确 Trace 时间单位、全局时间范围和待分析的相对 `0s-8s`。
3. 确认启动基准点与完成点。存在多个候选点时全部记录，说明最终选择依据。
4. 记录包名、进程名、PID/TID 映射。PID 可能复用时同时保留时间约束。
5. 建立分析目录和输入清单。

**门禁 G1**：无法定位目标进程或启动基准点时，只能输出“信息不足”和补采/补查项，不进入瓶颈判断。

### 2. 盘点已有脚本能力

先执行脚本帮助命令或阅读其接口说明，再用小范围查询验证。至少检查：

- 是否支持时间窗、进程、线程、类别和事件名过滤；
- 是否保留原始时间戳、持续时间、PID/TID、CPU、调度状态和父子切片关系；
- 是否解析异步事件、跨线程关联、binder/IPC、调度与频率信息；
- 是否会截断、聚合、去重、丢弃未知事件或改变时间精度；
- 输出能否定位回原始记录，如 row ID、slice ID、时间范围或查询条件；
- 大文件处理是否为流式/查询式，是否会一次性载入内存。

用一个已知小窗口做 sanity check：脚本统计结果必须能通过原始查询或另一工具复核。能力矩阵写入 `01-tool-capability.md`。

**门禁 G2**：关键字段缺失时，先补查询，不得把“脚本未显示”写成“事件不存在”。

### 3. 建立启动时间线

先宽后窄，只查询 `0s-8s` 必要字段：

1. 标记启动请求、进程创建/唤醒、运行时初始化、Ability/页面生命周期、首帧提交与显示等候选里程碑。
2. 建立主进程、关键线程、渲染相关线程及关键系统服务的泳道时间线。
3. 对每个阶段计算起止、墙钟耗时；不要把跨线程重叠耗时直接相加。
4. 标记空洞、长切片、密集短任务、IPC 等待、调度等待、I/O、锁等待和 CPU 竞争的候选区间。
5. 记录“启动总耗时”所采用的起止口径。

阶段命名优先采用 Trace 中可核验的事件名。平台语义参考 [analysis-playbook.md](./references/analysis-playbook.md)。

### 4. 从关键路径筛选候选问题

候选事件必须回答两个问题：

1. 它是否位于启动完成点的依赖路径上，或占用关键线程并推迟后继阶段？
2. 删除或缩短它，理论上是否可能推进完成点，而不是仅减少非关键并行工作？

对候选项按以下维度排序，不只按单次耗时：

- 关键路径贡献；
- 阻塞的后继里程碑；
- 重复次数与累计影响；
- 可归属层级：应用、框架/运行时、系统服务、内核/硬件、未知；
- 证据完整度与可复现性。

### 5. 分层深挖与交叉验证

对高优先级候选做二次查询，分析框架见 [analysis-playbook.md](./references/analysis-playbook.md)。至少覆盖：

- **应用侧**：主线程长任务、同步初始化、资源加载、I/O、锁、IPC、重复初始化、首帧前非必要工作、渲染与布局。
- **框架/运行时侧**：进程与运行时初始化、模块/字节码加载、GC/JIT/AOT相关事件、Ability和UI框架阶段。仅在 Trace 明示时使用具体术语。
- **系统侧**：进程调度、CPU 竞争/频率、内存压力、缺页、文件系统、binder/IPC 对端、图形合成及系统服务响应。

每个候选至少包含：

- 主证据：直接展示事件、等待或时序关系；
- 关联证据：证明它影响关键线程或后继里程碑；
- 反证检查：搜索能推翻当前解释的迹象；
- 交叉验证：原始查询、另一脚本、可比样本或重复采集之一。

**门禁 G3**：只有主证据、没有影响链时，降级为“观察项”，不得定性为启动瓶颈。

### 6. 建立证据账本

每条证据使用稳定 ID：`E-001`、`E-002`。每条问题使用 `F-001`，每条建议使用 `O-001`。

证据必须记录：来源文件、查询/脚本、过滤条件、绝对与相对时间、PID/TID、事件名、原始指标、输出文件、解释边界、可信度。

可信度分级：

- `高`：主证据与影响链均可直接核验，并有交叉验证；
- `中`：直接证据完整，但缺少对照样本或部分平台语义待确认；
- `低`：仅有相关性、聚合结果或单一脚本线索。

低可信度内容只能作为待验证假设，不能进入确定性问题清单。

### 7. 输出事实与问题描述

`04-factual-findings.md` 只允许出现：

- 启动口径与总览时间线；
- 已观测事实；
- 对关键路径的可证明影响；
- 归属边界与可信度；
- 尚缺证据的问题。

使用“观察到 X；X 在 Y 之前且阻塞/占用 Z；Y 随后于 T 发生”的证据化句式。禁止使用“显然、应该、可能是代码差”等无证据表述。

### 8. 输出可能的优化方向

`05-optimization-directions.md` 与事实文件分开。每条方向必须包含：

- 引用的问题 ID 和证据 ID；
- 建议动作及适用层级；
- 为什么可能缩短关键路径；
- 前置条件、风险和不能保证的部分；
- 最小验证实验；
- 成功指标与回归指标；
- 复采 Trace 时应观察的事件或阶段变化。

建议优先描述机制，不在缺少源码证据时指定具体函数改法。系统侧问题要区分“应用可规避”“平台需修复”“仅采集环境噪声”。

### 9. 最终一致性审查

逐项检查：

- 每个 `F-*` 是否引用至少一个 `E-*`；
- 每个 `O-*` 是否引用对应 `F-*` 与 `E-*`；
- 每个证据 ID 是否能通过记录的命令和过滤条件重现；
- 时间单位、基准点、PID/TID、启动类型是否前后一致；
- 是否误加重叠线程耗时；
- 是否把脚本缺失数据当作事件不存在；
- 是否把区间外事件、日志文本或平台常识当作当前样本事实；
- 事实文件是否混入建议；建议文件是否伪装成确定性收益承诺。

不满足任一项，回到证据账本修正后再交付。

## 模型工作方式

- 每轮只提出一个明确查询目标，避免一次导出所有事件。
- 查询结果先保存到文件，再给模型摘要、字段定义和少量相关行。
- 输出行数过多时先聚合，再按候选 ID 下钻。
- 工具报错或字段未知时停止解释，先检查 schema/help。
- 需要生成查询或审查结论时，使用 [prompt-library.md](./references/prompt-library.md) 中的提示词。
- 所有“未发现”表述都要附查询覆盖范围；否则改写为“当前查询未显示”。

## 停止条件

出现以下任一情况，停止下结论并列出补证计划：

- Trace 损坏、时钟域无法对齐或目标区间缺失；
- 无法识别目标进程、启动基准点或完成点；
- 脚本聚合不可回溯到原始事件；
- 关键事件被采集配置裁剪；
- 只有单次异常样本，且环境噪声无法排除；
- 证据之间冲突且无法通过追加查询解释。
