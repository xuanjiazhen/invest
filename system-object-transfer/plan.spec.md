# 仓颉与 ArkTS-Dyn 系统对象转换方案执行计划

## 1. 调研基线

| 材料 | 用途 |
|---|---|
| OpenHarmony `commonlibrary/ets_utils/base_sdk/transfer` | ArkTS 静动态转换入口、注册表和系统对象清单 |
| 各子系统 ANI/Taihe 与 NAPI 实现 | 确认两侧包装对象、native payload、身份与生命周期 |
| `docs_cangjie` 当前仓颉 API | 识别仓颉已提供的对象类型和接口 |
| `arkcompiler_cangjie_ark_interop` | 确认仓颉调用 ArkTS-Dyn 的对象表示和可用互操作接口 |
| ArkTS 静动态转换总结 | UIAbilityContext 双向转换的路径参考 |

所有源码事实记录仓库、提交号、文件和行号。网页只用于权威文档入口，源码实现以本地 OpenHarmony 工作树复核。

## 2. 范围

### 2.1 纳入

- 当前 ArkTS transfer 注册表中的系统对象；
- 当前仓颉 API 中已经公开的对象类型；
- 当前仓颉 API 与 ArkTS-Dyn API 之间共享 native 对象的交集；
- 应用自定义仓颉封装与直接互操作返回对象；
- 后续子系统新增类型的注册和扩展方法。

### 2.2 不纳入

- 尚未实现的仓颉 API；
- 不绑定 native 对象的普通 DTO、值类型和纯数据结构；
- 与对象转换无关的互操作语法、性能或代码生成方案；
- 未经源码或文档确认的未来对象清单。

## 3. 执行步骤

### 3.1 ArkTS 基线

1. 读取 `@ohos.transfer.ets` 与注册表实现，记录入口签名、查找方式、错误契约和反射调用。
2. 解析全部 `kitRegister/*.ets`，生成唯一 type key 清单及双向注册状态。
3. 选择 Context、Window、IPC、媒体、图形和 ArkUI 对象，追踪 static/dynamic 包装与 native payload。
4. 记录对象身份复用、引用持有、跨 VM 生命周期和失败路径。

### 3.2 仓颉 API 盘点

1. 从 `docs_cangjie` API 目录提取公开类、接口和句柄类型。
2. 与 ArkTS transfer type key、动态 API 类型及子系统 native 类型进行映射。
3. 对每个候选对象记录：仓颉类型、ArkTS-Dyn 类型、native 类型、创建接口、消费接口、转换方向和源码依据。
4. 分类为：当前必须支持、单向需要、已有原生桥接无需重复、无交集、证据不足。

### 3.3 接口设计

设计以下接口层次：

1. 应用调用层：泛型双向转换，目标类型由泛型参数表达；
2. 可扩展类型层：仓颉接口扩展或适配器声明 type key；
3. 子系统注册层：注册 native 提取、目标包装创建、身份缓存和释放回调；
4. 动态桥接层：承接直接互操作返回对象及用户自定义包装；
5. 错误层：未注册、类型不匹配、运行时不一致、native 对象失效和重复注册。

方案明确泛型约束、空值、异常、线程、VM/env、所有权、弱/强引用、幂等转换和 ABI 版本。

### 3.4 示例与验证

1. UIAbilityContext：仓颉 API 对象与 ArkTS-Dyn 对象双向转换；
2. 直接互操作返回对象：转换为仓颉 API 类型；
3. 用户自定义包装：通过扩展适配统一入口；
4. 子系统接入：注册转换器并复用同一 native 对象；
5. 错误示例：未注册类型和失效 native 对象。

代码示例区分“接口设计示意”和“最新仓颉 SDK 编译验证”。未执行真实编译的示例不得标注为可编译。

## 6. 验收条件

- 系统对象定义同时满足“双侧不同包装”和“共享同一 native 对象”；
- 对象清单仅包含当前已有接口，并可逐项追溯；
- 应用、用户自定义封装和子系统开发三类调用者均有完整路径；
- 泛型接口不依赖用户手写字符串 type key；
- 生命周期、VM/env、线程和错误契约明确；
- 双向转换保持 native 对象身份，不复制业务状态；
- 报告末尾给出设计、开发、测试人日、小计、总计和排期；
- 报告与 slides 不包含调查时间线或历史修订描述；
- HTML 可渲染，index 只链接 HTML slides。
